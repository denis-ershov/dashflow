# Модель угроз и меры защиты DashFlow Hub

## Область действия

Документ описывает HTTP/SQLite Hub и его границу с расширением, локальными агентами, webhook-отправителями и, при отдельной настройке, reverse proxy. Hub рассчитан прежде всего на локальный запуск. Он не является SaaS с изоляцией арендаторов. Контракт маршрутов — [`hub/openapi.yaml`](../hub/openapi.yaml), детали установки и CLI — [`HUB_OPERATIONS.md`](HUB_OPERATIONS.md).

## Активы и нарушители

Защищаемые активы: содержимое items и boards, журнал изменений и истории, токены доступа, pairing challenge, webhook token/signing key, SQLite-файл, конфигурация allowlist и audit-журнал.

Рассматриваются локальный процесс под другой учётной записью, расширение или агент с ошибочно избыточным scope, злоумышленник с украденным токеном, внешний отправитель webhook, а также сетевой клиент при ошибочном открытии Hub на интерфейс LAN/Internet. Компрометация учётной записи ОС, процесса Hub или его конфигурации выходит за границу изоляции Hub и может дать доступ к данным и credential-файлам.

## Границы и базовые настройки

- По умолчанию Hub слушает `127.0.0.1:47831`; конфигурация принимает IP-адрес и может быть переопределена только явной настройкой. Loopback не защищает от других процессов того же пользователя.
- При удалённом доступе порт Hub должен оставаться закрытым от прямого внешнего доступа; используйте TLS reverse proxy, firewall и ограниченный upstream. Hub не считает `X-Forwarded-*` доказательством личности; `trustProxy` выключен.
- Для браузера разрешены только заранее заданные точные extension origins. Wildcard CORS не используется. Preflight проверяет методы и allowlist заголовков. Origin ограничивает браузерный контекст, но не заменяет токен и не защищает от локального небраузерного клиента.
- Конфиг и база хранятся в профиле пользователя. На POSIX каталог создаётся с режимом 0700, JSON-конфигурация и база — 0600; на Windows используются ACL пользователя. Запускать сервис следует с минимальными правами, без повышения привилегий.
- Ответы устанавливают `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`. Ошибки скрывают внутренние исключения и SQL-детали. Логи Hub не включают тела запросов и токены.

## Аутентификация и управление секретами

Bearer-токен создаётся CLI или через pairing, генерируется криптографически стойким генератором, в базе хранится только SHA-256 digest. Секрет показывается при создании один раз. При проверке учитываются отзыв и срок действия; `last_used_at` обновляется при успешной аутентификации. Выдавайте только необходимые scopes и задавайте срок действия там, где это удобно для процесса.

Pairing-код имеет шесть цифр, хранится как scrypt-хеш с солью, живёт пять минут, ограничен десятью неудачными попытками и после успешного обмена удаляется. Он может быть привязан к точному Origin расширения. Endpoint дополнительно ограничен 10 запросами в минуту на IP и 30 в минуту глобально.

Webhook использует два независимых секрета: случайный token в URL маршрута и signing key. В базе webhook token хранится как hash; signing key необходим серверу для проверки HMAC и хранится в базе. Отзыв webhook обнуляет ключ подписи. Сигнатура HMAC-SHA256 вычисляется по `timestamp.delivery.` и неизменённым байтам тела, сравнивается constant-time; timestamp принимается в окне ±5 минут. Delivery id ограничен форматом и используется для идемпотентности. Запросы с Origin отклоняются.

Не помещайте токены и секреты в URL, shell history, логи, снимки экрана, публичные репозитории и клиентские bundle. Токен пути webhook — вынужденное исключение контракта URL, поэтому прокси/серверные access logs должны маскировать путь `/v1/webhooks/in/{token}`. При утечке токена отзовите его через CLI и выдайте новый; при утечке webhook-credential отзовите webhook и создайте замену. Не копируйте рабочую базу или секреты в тестовые среды.

## Авторизация и доступ к данным

Scopes проверяются на каждом маршруте сервером; скрытие UI-функции не является защитой. Токен без необходимого scope получает отказ. Рекомендуется отдельный токен для каждого агента/интеграции с минимальным scope.

Модель доступа в текущем коде не изолирует все операции по владельцу:

- Списки и чтение item доступны всем токенам с `items:read`; фильтрация по owner отсутствует.
- `PATCH item` требует `items:write`, проверяет owner id и версию `If-Match`; для изменения чужой записи требуется `items:manage`.
- Для публикации дайджеста требуется `digests:write`. Область проверяется и на общем маршруте создания Item.
- `DELETE item` требует `items:manage` и выполняет мягкое удаление; проверка `If-Match` опциональна.
- Board list/get/update проверяют `boards:read`/`boards:write`, но репозиторий не сравнивает owner доски с principal и не требует версию при update. Не выдавайте `boards:write` недоверенному principal при необходимости строгой изоляции досок.
- `sync` открывает общий журнал `/v1/changes`, историю по ID и пакетную запись sync; это широкая привилегия для Hub, а не доступ только к собственным данным.
- Новые items принадлежат principal id токена или webhook. Синхронное обновление сохраняет owner существующей записи, а новая запись получает owner отправителя.

Эти ограничения — важная граница модели угроз. Hub не должен считаться безопасной многопользовательской сетью с взаимной конфиденциальностью данных. Наиболее безопасный профиль — один доверенный владелец Hub и отдельно выданные токены с узкими scopes.

## Валидация, нагрузка и сетевые атаки

Внешние JSON/query/header значения валидируются на сервере; для объектов запрещены лишние поля. ID, версии, URL, даты, idempotency keys, enum и размеры проверяются до вызова хранилища. SQLite использует подготовленные выражения и параметризованные значения. Максимальный размер тела — 256 KiB; timeout запроса — 15 секунд; максимальная длина параметра маршрута — 256.

По умолчанию записывающие HTTP-операции ограничены 60/мин на токен. Конфигурация разрешает 1–10 000/мин. Неуспешная аутентификация ограничена 120/мин на IP; pairing — 10/мин на IP и 30/мин глобально; webhook — 120/мин на IP и настроенный write limit на webhook; WS handshake — 120/мин на IP и максимум 256 активных соединений. Лимитеры хранят состояние в памяти процесса, поэтому не заменяют rate limiting на perimeter для сетевого развёртывания и не координируются между экземплярами.

WebSocket ограничен payload 1024 байт, отключает per-message compression, требует аутентификацию в течение пяти секунд и закрывает соединение при невалидном/бинарном сообщении, отзыве токена либо буфере отправки свыше 64 KiB. Токен активности проверяется при ping и при отправке уведомлений. Клиентский протокол после auth — только `ping`; сервер отвечает `pong` и `changes` с sequence.

Webhook ограничен 256 KiB и проверяет HMAC до разбора JSON. Ограничение timestamp сужает окно replay, а delivery id и идемпотентность предотвращают повторное создание одного события. Отправители должны генерировать уникальный delivery id и повторно использовать его для ретраев той же доставки.

## Персональные данные, журналирование и хранение

Hub хранит пользовательское содержимое, метаданные источника/владельца, токен-метаданные, хеши credential, webhook signing keys, журнал изменений, истории конфликтов и аудит. Содержимое items и журнал синхронизации доступны по широким scopes, описанным выше. Ограничьте файловый доступ к каталогу Hub и резервным копиям.

Audit-записи фиксируют principal, действие, entity id и исход операции для записывающих HTTP-запросов; внутренние операции токенов, pairing и webhook также добавляют audit events. Ответы не содержат stack trace. При сбое записи HTTP audit событие логируется как ошибка, но результат уже завершённой записи не откатывается. Логи приложения не должны содержать Authorization, pairing code, webhook token/signing key или тела запросов; отдельно проверьте access logs reverse proxy, поскольку webhook token находится в path.

SQLite работает в WAL режиме, транзакции используют `BEGIN IMMEDIATE`, busy timeout равен 5 секундам. Резервное копирование должно учитывать согласованность SQLite и sidecar-файлов; процедуру остановки/копии/восстановления см. `docs/HUB_OPERATIONS.md`. Период хранения и автоматическое удаление audit/history в текущем Hub не заданы; защищайте диск и резервные копии соответствующим образом.

## Миграции, восстановление и реагирование

База создаётся при первом запуске. Реализована схема версии 1; неизвестная версия приводит к отказу запуска. Перед будущей миграцией сделать проверенную резервную копию и определить совместимость с версией приложения. Автоматического downgrade нет. При неудачном развёртывании сначала остановите Hub, сохраните диагностические данные без секретов и восстановите согласованную резервную копию либо верните совместимую версию приложения. Не удаляйте таблицы и не понижайте `user_version` вручную.

При подозрении на компрометацию: отзовите затронутые token/webhook credentials, выпустите замену, ограничьте сетевой доступ, сохраните audit и системные журналы с ограниченным доступом, проверьте резервные копии и определите возможный объём прочитанных/изменённых данных. Не отправляйте секреты в тикеты или логи.

## Проверки и статус подтверждений

По сообщению владельца задачи серверные тесты и три повтора E2E с двумя синтетическими Chromium-профилями прошли. E2E временно разрешал loopback-хост и проверял реальный Origin, WebSocket, восстановление очереди после 503 и конфликт версий. Тестовые профили синтетические; реальные пользовательские данные и credentials не включаются в репозиторий. Это не является подтверждением Firefox, NVDA, Docker-образа либо публичного сетевого развёртывания; эти сценарии отдельно не заявлены как проверенные.
