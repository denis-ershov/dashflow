### Общие правила для всех этапов

- **Definition of Done шага:** tsc, eslint, prettier, unit/component-тесты, сборка Chrome и Firefox, E2E smoke; новый UI — ru/en, состояния loading/empty/error/offline, клавиатура, ширина от 280 px до 4K; CHANGELOG; архитектурный документ, если меняется архитектура.

- **Внешние данные** (API, агенты, коннекторы, импорт) читаются через `jsonReaders` / валидаторы, Markdown рендерится только через санитайзер.

## Этап 1. Фундамент рабочего пространства — 3.9.0

**Цель:** одна модель данных для всего, что пользователь и агенты кладут в рабочее пространство, и инфраструктура вокруг неё: команды с отменой, несколько дашбордов, поиск.
**Вне scope:** синхронизация с Hub (этап 3), новые виджеты (этап 2), привычки — остаются в текущем формате (у них своя модель «история по дням»).

### 1.1. Хранилище Item (≈2 дня) — ✅ выполнено 2026-10-30

> Отклонение от плана: порядок — библиотека `fractional-indexing` вместо собственного алгоритма (у простой «середины» ключ растёт линейно при добавлении в конец). `ItemPatch` очищает поля через `null`. Подробности — `ITEMS_ARCHITECTURE.md`, ADR-017.

Новый модуль `src/core/items/`:

| Файл | Ответственность |
|---|---|
| `types.ts` | `Item`, `ItemKind`, `ItemSource`, `Board`, `ItemQuery`, `ItemChange` |
| `ids.ts` | ULID на `crypto.getRandomValues` (сортируемый по времени, без зависимости) |
| `validation.ts` | Проверка входящего Item (лимиты, допустимые kind/status, http(s)-ссылки) — для UI, импорта, позже Hub и агентов |
| `db.ts` | IndexedDB `dashflow_items` v1 через `idb` (уже в зависимостях): stores `items`, `boards`, `changes` |
| `repository.ts` | CRUD, запросы, мягкое удаление, очистка корзины старше 30 дней |
| `events.ts` | `BroadcastChannel('dashflow-items')`: изменения видят все открытые вкладки и сервис-воркер |
| `useItems.ts` | React-хук `useItems(query)` с подпиской на изменения |

```ts
type ItemKind = 'task' | 'note' | 'link' | 'reminder' | 'digest' | 'article' | 'card';

interface Item {
  id: string;                    // ULID
  kind: ItemKind;
  title: string;                 // ≤ 500 символов
  body?: string;                 // Markdown, ≤ 100 000
  url?: string;                  // только http(s)
  status: string;                // 'inbox' | 'todo' | 'doing' | 'done' | колонка доски
  boardId?: string;
  order: string;                 // дробный индекс для порядка внутри колонки без перенумерации
  priority?: 'low' | 'medium' | 'high';
  dueAt?: string; remindAt?: string;          // ISO 8601 с часовым поясом
  tags: string[];
  source: { type: 'user' | 'agent' | 'connector' | 'import'; id: string; name: string };
  pinned?: boolean;
  createdAt: string; updatedAt: string;
  archivedAt?: string; deletedAt?: string;    // мягкое удаление
  version: number;               // +1 на каждое изменение — для конфликтов на этапе 3
}

interface Board { id: string; title: string; columns: { id: string; title: string; wipLimit?: number }[]; createdAt: string }
interface ItemChange { seq: number; itemId: string; op: 'create' | 'update' | 'delete'; version: number; at: string; source: Item['source'] }
```

- Индексы `items`: `kind`, `status`, `boardId`, `updatedAt`, `remindAt`, `deletedAt`.
- Журнал `changes` (autoIncrement `seq`) — основа отмены, аудита и будущей синхронизации; хранит последние 5 000 записей.
- `navigator.storage.persist()` при первом запуске хранилища, чтобы браузер не вытеснял данные; обработка `QuotaExceededError` с понятной ошибкой.

**Тесты:** `fake-indexeddb` в unit-тестах (dev-зависимость, ADR) — CRUD, запросы по индексам, мягкое удаление, очистка корзины, валидация на границах лимитов, BroadcastChannel-уведомления.
**Готово, когда:** репозиторий покрыт тестами ≥ 90%, валидация отвергает невалидные Item, две вкладки видят изменения друг друга.

### 1.2. Команды и отмена (≈1,5 дня) — ✅ выполнено 2026-10-30

> Отклонения: команды `space.*` переносятся в шаг 1.5 (пространств ещё нет); командная палитра переходит на общий реестр вместе с поиском в шаге 1.6. Повтор (redo) — вне scope (ADR-018).

Модуль `src/core/commands/`: всё, что меняет данные, проходит через `dispatch(command)`.

```ts
interface CommandDefinition<P, R> {
  type: string;                       // 'item.create', 'item.move', 'space.switch'…
  validate(payload: unknown): P;      // бросает CommandValidationError
  execute(payload: P, ctx: CommandContext): Promise<{ result: R; undo?: () => Promise<void> }>;
}
```

- Команды этапа 1: `item.create`, `item.update`, `item.move` (колонка/порядок), `item.complete`, `item.snooze`, `item.archive`, `item.delete`, `item.restore`, `board.create`, `board.update`, `space.create`, `space.rename`, `space.switch`, `space.delete`.
- `CommandContext.source` — кто вызвал (user / agent / connector / import), попадает в `changes` и в `Item.source` при создании.
- Отмена: стек последних 50 операций в сессии вкладки, `Ctrl+Z` вне полей ввода и кнопка «Отменить» в тосте после удаления/архивации/перемещения.
- Командная палитра получает команды из того же реестра (единый источник подписей и горячих клавиш).

**Тесты:** каждая команда — выполнение, отмена, отказ на невалидных данных; повторная отмена ничего не ломает.
**Документы:** ADR-018 «Командная шина и отмена».

### 1.3. Миграция существующих данных (≈1 день) — ✅ выполнено 2026-10-30

> Отклонения: маркер хранится в store `meta` базы Item и пишется одной транзакцией с данными (атомарность вместо маркера в `chrome.storage`); запуск миграции при старте переносится в шаг 1.4 — вместе с переключением виджетов, чтобы они не писали в старые ключи после переноса. Заметки и ссылки получают статусы `active`/`saved`.

- Задачи Todo (общий ключ и копии экземпляров) → `kind: 'task'`, доска «Задачи» на каждый экземпляр виджета; заметки → `kind: 'note'`; быстрые ссылки → `kind: 'link'`.
- Идемпотентно: маркер `dashflow_items_migration_v1`, повторный запуск ничего не дублирует; при ошибке — откат транзакции, старые данные не трогаются.
- Старые ключи не удаляются до 3.10.0 (откат на 3.8 видит прежние данные).
- Экспорт **3.0**: раздел `items` + `boards`; импорт 2.0–2.2 конвертирует старое содержимое тем же кодом миграции.

**Тесты:** миграция с фикстурами 3.8 (пусто, один экземпляр, несколько экземпляров, битые данные), повторный запуск, импорт 2.2 → 3.0, экспорт → импорт.

### 1.4. Виджеты на Item (≈1,5 дня) — ✅ выполнено 2026-10-30

> Отклонения: архивация доски при удалении виджета не сделана — у нового экземпляра другой id, восстановить привязку нечем; доски без виджета останутся видны в Kanban (этап 2). Стартовое содержимое — только в новом профиле. Главный чанк вырос на 30 КБ (см. CHANGELOG), разбор — этап 7.

- **Todo:** список = доска экземпляра (`settings.boardId`); фильтры и сортировка — запросами `useItems`; привычки — без изменений.
- **Notes:** `settings.itemId`, текст — `body` заметки; автосохранение командой `item.update` с дебаунсом (в стек отмены не попадает каждое нажатие — только «сеанс правки»).
- **QuickLinks:** ссылки доски экземпляра, порядок — `order`.
- Удаление виджета сохраняет его записи и доску. Доски без виджета будут видны в Kanban с шага 2.2.

### 1.5. Spaces — несколько дашбордов (≈1,5 дня) — выполнено 2026-11-23

- Состояние: `spaces: { id, title, icon?, instances, layouts }[]`, `activeSpaceId`; миграция стора дашборда v2 → v3 (текущая раскладка становится Space «Главная»), бэкап в `DASHBOARD_BACKUP_V2`.
- Переключатель в доке (список + «Новое пространство»), командная палитра, горячие клавиши **Alt+1…9** (`Ctrl+1…9` браузер забирает себе; в Chrome для Linux `Alt+цифра` тоже переключает вкладки — там остаются док и палитра).
- Hero и обои — общие для всех пространств (решение по умолчанию; настраиваемость — этап 6).
- Экспорт 3.0 включает все пространства.
- Новое пространство получает пустую сетку. Настройки колонок и отступов сохраняются вместе с ней. Удаление раскладки требует подтверждения и сохраняет записи Item.

**Тесты:** миграция v2 → v3, переключение, удаление активного пространства, последнее пространство удалить нельзя; E2E: создать пространство, перезагрузить, оно на месте.

### 1.6. Глобальный поиск (≈1 день) — выполнено 2026-11-23

- Командная палитра ищет по Item (title, body, tags, url), виджетам, пространствам и командам; группы результатов, переход к элементу (открыть заметку, подсветить задачу).
- Индекс в памяти, строится по запросу и обновляется по `BroadcastChannel`; ранжирование: точное совпадение > префикс > вхождение, свежие выше. Без новой зависимости, пока элементов < 10 000 (замер на 10 000 — в тестах производительности).
- Поиск по умолчанию исключает архив и корзину. Если у результата нет доступного виджета, палитра открывает карточку записи.

`docs/ITEMS_ARCHITECTURE.md` (модель, хранилище, события, миграция, лимиты, риски), ADR-017 «Item и IndexedDB», ADR-018, обновление `STORAGE_ARCHITECTURE.md`, `BACKUP_STRATEGY.md` (экспорт 3.0), `CORE_ARCHITECTURE.md`. Релиз **3.9.0**.

## Этап 2. Виджеты рабочего пространства — 3.10.0

**Цель:** то, ради чего всё затевалось, — единое место для входящего, задач, напоминаний и чтения.
Все виджеты — представления над Item; новых хранилищ не появляется.

### 2.1. Inbox (≈2 дня) — реализовано 2026-11-23

- Лента `status: 'inbox'` из всех источников, значок источника (вы, агент, коннектор), группировка по дням.
- Действия: в задачи (выбор доски), запланировать (дата → `dueAt`), напомнить, архив, удалить; массовый выбор; клавиатура `j/k`, `e` (архив), `t` (в задачи).
- Быстрый ввод вверху: строка с разбором `завтра 10:00`, `#тег`, `!` (высокий приоритет) — разбор в `core/items/quickParse.ts` с тестами на ru/en.
- Пустое состояние «Входящие разобраны» — цель «Inbox zero».

### 2.2. Kanban (≈3 дня) — реализовано 2026-11-23

- Доска по `boardId`: колонки из `Board.columns`, карточки — Item, порядок — `order` (дробные индексы).
- Перетаскивание мышью, касанием и **с клавиатуры** (пробел — взять, стрелки — двигать, пробел — положить, Escape — отмена) с объявлениями для скринридера.
- Библиотека: `@dnd-kit/core` + `@dnd-kit/sortable` — **решение D1**, ADR-020. Альтернатива — собственная реализация на Pointer Events.
- Карточка: заголовок, теги, срок (просрочено — акцент), приоритет; открытие — боковая панель с Markdown-описанием.
- WIP-лимиты колонок, свёртывание колонок, на узком экране — колонки списком с переключателем.

### 2.3. Напоминания (≈2 дня) — реализовано 2026-11-23

- Права `alarms` (обязательное, без предупреждения при установке) и `notifications` (необязательное, запрос при первом напоминании).
- Сервис-воркер: при изменении `remindAt` (событие из `BroadcastChannel` или при старте) ставит `chrome.alarms` на ближайшие напоминания; по срабатыванию — системное уведомление с кнопками «Готово» и «Через час» (команды `item.complete` / `item.snooze` выполняются прямо в воркере — `core/items` не зависит от React).
- Без права на уведомления — напоминание появляется в Inbox и бейджем на иконке.
- Firefox MV2: фоновая страница вместо воркера — тот же код; кнопки уведомлений в Firefox не поддерживаются → клик по уведомлению открывает задачу.

### 2.4. Дайджест (≈1,5 дня) — реализовано 2026-11-23

- `kind: 'digest'`: заголовок, секции Markdown, ссылки на источники, «прочитано»; виджет показывает последний непрочитанный дайджест и архив.
- Источники сейчас: ручной (шаблон «Утро»: погода + задачи на сегодня + новое в лентах, собирается локально по кнопке/расписанию); на этапе 4 — агенты.
- Расписание выключено по умолчанию. При включении выпуск собирается в 07:30 по местному времени. Погода и новости берутся из кеша, один выпуск на местный день. [Архитектура дайджеста](DIGEST_ARCHITECTURE.md)

### 2.5. Читалка лент (≈2 дня) — реализовано 2026-11-24

- Развитие RSS: непрочитанное (хранится по id статьи, лимит 5 000), «прочитать позже» → `kind: 'article'` в Inbox, режим чтения в модальном окне (описание из ленты, санитайзер, без загрузки страницы целиком).
- Фоновое обновление лент в воркере по `chrome.alarms` (раз в 30 мин), счётчик непрочитанного на вкладке виджета.
- Виртуализация списка при > 100 элементов.
- Кеш лент хранится до 48 часов. Фоновое обновление соблюдает ранее выданные разрешения для хостов. `refreshInterval=0` оставляет ручное обновление. Указывайте конечный URL ленты. [ADR-022](adr/ADR-022-rss-background-parser.md)

### 2.6. Повестка дня (≈2 дня) — реализовано 2026-11-23

- Календарь по ICS-ссылке (Google, Outlook, iCloud дают секретный адрес): доступ к хосту — необязательное право по клику, как у RSS.
- Разбор ICS: события, часовые пояса, простые повторения (`DAILY`, `WEEKLY` с `BYDAY`, `COUNT`/`UNTIL`) — собственный парсер. Сложные правила получают явную пометку. Секретный URL хранится локально вне экспорта. [ADR-021](adr/ADR-021-ics-agenda.md)
- Сегодня/неделя, задачи с `dueAt` на той же шкале, «следующее событие через 25 мин» в Hero (опционально).

**Документы:** `WIDGET_CATALOG_ARCHITECTURE.md`, ADR-020 (DnD), ADR-021 (ICS), обновление `PRIVACY*` и `CHROMEWEBSTORE.md` (alarms, notifications, хосты календаря). Скриншоты листинга — пересъёмка. Релиз **3.10.0**, старые ключи Todo/Notes/Links удаляются миграцией.

**Критерии приёмки этапа 2:** напоминание приходит при закрытой вкладке DashFlow; Kanban полностью управляется с клавиатуры (проверка скринридером NVDA); лента с 1 000 статей прокручивается без подтормаживаний; повестка корректна при смене часового пояса.

## Этап 3. DashFlow Hub и собственное API — 4.0.0

**Цель:** точка, через которую внешние программы (агенты, коннекторы, скрипты) читают и пишут Items, а расширение синхронизируется с ней.

### 3.1. Монорепозиторий — реализовано

- npm workspaces: `packages/shared` (типы `Item`, валидаторы, контракт API — общие для расширения и Hub), `hub/` (сервис). Расширение остаётся в корне, сборка WXT не меняется.
- Общие валидаторы переезжают из `src/core/items/validation.ts` в `packages/shared` (один источник правды для клиента и сервера).

### 3.2. Сервис — реализовано локально

- Node ≥ 22.13, **Fastify**, хранилище **`node:sqlite`** (встроен в Node, без нативной сборки) — **решение D3**; альтернатива — `better-sqlite3` (зрелее, но нативный модуль под каждую ОС).
- Таблицы: `items`, `boards`, `changes` (seq), `tokens` (sha256, scopes, имя, последний доступ), `audit`, `webhooks`.
- Конфигурация: `~/.dashflow-hub/config.json` (права 0600) + переменные окружения; слушает **только 127.0.0.1** по умолчанию.
- Запуск: `npx dashflow-hub`, автозапуск (инструкции для Windows Task Scheduler, systemd, launchd), Docker-образ для VPS.

### 3.3. REST API v1 — реализовано

| Метод | Путь | Область | Описание |
|---|---|---|---|
| GET | `/v1/items?kind=&status=&boardId=&q=&cursor=&limit=` | `items:read` | Список с курсорной пагинацией |
| GET | `/v1/items/:id` | `items:read` | Один элемент |
| POST | `/v1/items` | `items:write` | Создать (заголовок `Idempotency-Key`) |
| PATCH | `/v1/items/:id` | `items:write` | Изменить (`If-Match: version`) |
| DELETE | `/v1/items/:id` | `items:manage` | Мягкое удаление |
| GET/POST/PATCH | `/v1/boards…` | `boards:*` | Доски |
| POST | `/v1/digests` | `digests:write` | Опубликовать дайджест |
| GET | `/v1/changes?since=seq` | `sync` | Журнал изменений для синхронизации |
| POST | `/v1/sync/push` | `sync` | Пакет изменений от расширения |
| POST | `/v1/webhooks/in/:token` | — (секрет в пути + HMAC) | Входящий вебхук → Item в Inbox |
| GET | `/v1/health` | — | Проверка живости |

- Ошибки: `{ error: { code, message, details? } }`, коды `VALIDATION_FAILED`, `NOT_FOUND`, `CONFLICT`, `FORBIDDEN`, `RATE_LIMITED`.
- Агенты по умолчанию меняют только свои записи (`source.id` = id токена); `items:manage` — отдельная выдача.
- Rate limit на токен (по умолчанию 60 запросов/мин на запись), лимиты размера тела 256 КБ.
- `hub/openapi.yaml` (OpenAPI 3.1) — источник правды; `docs/API_ARCHITECTURE.md`.

### 3.4. Синхронизация с расширением — реализовано

- Сопряжение: в настройках «Подключить Hub» → адрес + одноразовый 6-значный код, который показывает `dashflow-hub pair` → токен устройства (`sync`), хранится в `chrome.storage.local`.
- Право на хост Hub (`http://127.0.0.1/*` или адрес VPS) — необязательное, запрос при сопряжении.
- Клиент в сервис-воркере: при наличии открытой вкладки — WebSocket `/v1/stream` (события изменений), иначе — опрос `changes?since` по `chrome.alarms` раз в 5 мин; очередь исходящих команд в IndexedDB, повтор с экспоненциальной задержкой.
- Конфликты: побеждает большая `version`, при равенстве — версия Hub. Проигравшая версия сохраняется в `item_history` на Hub или `itemHistory` расширения и доступна в карточке Kanban («Есть более ранняя версия»).
- Статус синхронизации в доке (подключено / офлайн / ошибка) и на странице диагностики.

### 3.5. Безопасность — реализовано для локальной поставки

- Модель угроз (`docs/HUB_SECURITY.md`): локальные процессы, вредоносный контент от агентов, утечка токена, флуд, Hub на VPS (только за HTTPS, Caddy).
- Токены: показываются один раз, отзыв, срок действия по желанию; журнал аудита по каждому запросу на запись.
- CORS: разрешён только origin расширения (`chrome-extension://<id>`, `moz-extension://<uuid>`), остальное — без CORS (агентам он не нужен).

**Тесты:** API-тесты на каждый маршрут (позитивные, невалидные, без прав, чужие записи, конфликт версий, идемпотентность), тест синхронизации двух клиентов, нагрузочный smoke (1 000 запросов/мин).
**Релиз:** расширение **4.0.0** (синхронизация — опционально, без Hub всё работает как раньше), Hub **0.1.0** (npm + GitHub Release + Docker).

**Локальная приёмка.** Серверный набор включает 1 000 авторизованных чтений через Fastify Inject. Два синтетических профиля Chromium проверяют фактический Origin REST/WS, офлайн-очередь и конфликт. npm-пакет Hub устанавливается отдельно от монорепозитория. Публикация, запуск контейнера и эксплуатация на VPS требуют проверки в соответствующем окружении.

## Этап 4. ИИ-агенты — 4.1.0

**Цель:** Hermes Agent, OpenClaw, Claude Code и любые MCP-клиенты читают и наполняют рабочее пространство безопасно и предсказуемо.

### 4.1. MCP-сервер — реализовано

- В Hub, на `@modelcontextprotocol/sdk`: транспорты stdio (`dashflow-hub mcp`) и Streamable HTTP (`/mcp`, тот же токен и области).
- Инструменты (JSON Schema, описания для модели — ru/en):
  `list_items`, `search_items`, `get_item`, `create_item`, `update_item`, `complete_task`, `move_card`, `create_reminder`, `publish_digest`, `list_boards`, `get_agenda`.
- Ресурсы: `dashflow://inbox`, `dashflow://board/{id}`, `dashflow://today`.
- Ответы инструментов — компактные (без лишних полей), с лимитом количества.

### 4.2. Подключение агентов — руководства готовы

- На этом шаге — сверка с актуальной документацией Hermes Agent и OpenClaw (способ подключения MCP / HTTP-инструментов, формат skill).
- `docs/agents/hermes.md`, `docs/agents/openclaw.md`, `docs/agents/claude-code.md`: конфиг, выдача токена, проверка.
- OpenClaw: skill `dashflow` (SKILL.md) поверх MCP.

### 4.3. Сценарии — примеры готовы

`docs/agents/recipes/`: утренний дайджест (погода, повестка, задачи на сегодня, новое в лентах и GitHub → `publish_digest` к 7:30), разбор Inbox (предложить доску и срок, но не переносить без подтверждения), недельный обзор задач, «прочитать позже» → конспект в заметку. Для каждого — промпт, нужные области токена, ожидаемый результат.

### 4.4. Задачи агентам из расширения — реализовано

- «Поручить агенту» в командной палитре и в меню карточки: Item с `assignee: 'agent:<id>'` и `status: 'todo'`.
- Агент получает их через `list_items({ assignee: 'me' })`, отвечает `update_item` (комментарий, статус) или дайджестом.

### 4.5. Страница «Агенты» — реализовано

- В настройках (данные из Hub): агенты-токены, области, последняя активность, число созданных записей, «Отозвать», «Откатить операции агента за период» (команды из журнала `changes`).
- На карточках — значок агента-источника, фильтр по источнику в Inbox.

**Безопасность и качество (правила 96–97).** Содержимое лент и писем считается недоверенными данными. Агент без `items:manage` обновляет свои записи и разрешённые поля назначенной ему задачи. Регрессионные тесты проверяют схемы, области доступа и отзыв токена. Метрика продукта — доля дней, когда дайджест опубликован к 7:30.

**Приёмка.** Stdio и Streamable HTTP проверены через MCP SDK с синтетической SQLite. Подключение Hermes Agent, OpenClaw и Claude Code описано с опорой на документацию клиентов. Управляемый откат ограничен журналом, записанным после миграции Hub SQLite v2. [Архитектура MCP](MCP_ARCHITECTURE.md)

## Этап 7. Оптимизация (по замерам)

**Базовая линия (2026-10-30):** главный чанк 742 КБ, CSS 104 КБ, пакет 1,74 МБ; LCP новой вкладки — замерить.

**Контрольный замер 3.9.0 (2026-11-23).** Главный JS 798 621 Б и 215 292 Б gzip, CSS 105 296 Б и 16 028 Б gzip, пакет Chrome 1 001 776 Б. В Chromium с загруженным расширением и заблокированными внешними запросами медиана LCP составила 280 мс при первом открытии и 120 мс при перезагрузке. Медиана появления первого элемента сетки составила 147 и 60 мс. Три отдельных временных профиля, по одной паре навигаций в каждом. TTI и память при 20+ виджетах ещё предстоит измерить.

**Контрольный замер 3.10.0 (2026-11-24).** После отложенной загрузки закрытых панелей стартовый JS, включая предзагрузку, сократился с 257 347 до 243 982 Б gzip. CSS — 16 498 Б gzip, пакеты Chrome и Firefox — около 1,21 МБ каждый. Медиана тёплого LCP в Chromium составила 208 мс.

## Риски

| Риск | Влияние | Мера |
|---|---|---|
| Потеря данных при миграции на Items | Высокое | Транзакция, маркер, старые ключи до 3.10, тесты на фикстурах, экспорт перед обновлением в чеклисте релиза |

| Изменения WXT/браузеров ломают сборку | Среднее | E2E на собранном пакете (уже поймал одну такую поломку), Dependabot, закреплённый раннер CI |
