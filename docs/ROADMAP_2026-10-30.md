# DashFlow: готовность к продакшену и план развития — 2026-10-30

Исходные данные: документация `docs/`, сверенная с кодом `main` (f787735, v3.7.3, 678 тестов, eslint/tsc чистые).
Цель владельца: самое красивое и удобное рабочее пространство в новой вкладке — прежде всего для себя. Сюда стекаются дайджесты, ленты, напоминания и доски задач, а ИИ-агенты (Hermes Agent, OpenClaw и др.) читают и обновляют контент через собственное API.

**Профиль продукта (правило 114):** личный инструмент, который параллельно публикуется в Chrome Web Store и AMO. Отсюда два следствия:
- требования магазинов и безопасность обязательны;
- SLO, мониторинг и аналитику не раздуваем: метрики уровня SaaS здесь не нужны.

## 1. Готовность к продакшену

### 1.1. Что уже в порядке

- **Качество:** TS strict, ESLint, Prettier, 98 тестовых файлов (unit, component, integration, performance), guard-тесты дизайн-системы и i18n.
- **CI и релиз:** CI собирает Chrome MV3 и Firefox MV2, релизный workflow запускается по тегу, архив исходников для AMO готов.
- **Безопасность:** iframe изолирован в песочнице без `allow-same-origin`, RPC проверяет `event.source`, права плагинов выдаются через окно согласия. Пользовательский CSS проходит санитайзер, обои валидируются, импорт содержимого проверяет каждое значение.
- **Локализация:** полная ru/en, мн. число через `Intl.PluralRules`, даты и время через `Intl`.
- **Данные:** миграции стора дашборда, экспорт и импорт 2.2 с содержимым виджетов, `CrashLogger` с маскировкой PII.

### 1.3. Что ещё не покрыто

- **Нет E2E на настоящем расширении.** Все тесты идут в jsdom, а `chrome.*` API, CSP, сервис-воркер и сборку не проверяет ни один тест. Нужен Playwright smoke: загрузить `.output/chrome-mv3` и проверить, что новая вкладка рендерится, а виджет добавляется и сохраняется после перезагрузки.
- **Нет порога покрытия:** в `vitest.config.ts` нет секции `coverage`, CI покрытие не считает.
- **Цепочка поставки:** actions закреплены по тегу (`@v4`), а не по SHA. В CI нет `npm audit` или Dependabot, нет сканера секретов. Node 20 скоро выйдет из LTS.
- **Чистота кода:** 7 мест с `any` (в основном `background.ts`), `console.log` в воркере.
- **Квота хранилища:** IndexedDB без `unlimitedStorage`, при переполнении квоты падение. Сценарий `QuotaExceededError` не обработан и не протестирован.
- **Документы для вымышленных процессов.** `SLO.md`, `MONITORING.md`, `BACKUP_STRATEGY.md`, `DEPLOYMENT_PROCEDURES.md` (≈2 200 строк) описывают Google Sheets-дашборды, PowerShell-мониторинг API, постмортемы «Week 42» и ожидаемый размер бандла 600–800 КБ (реально 1,66 МБ). Это противоречит правилу «документация отражает текущее состояние». Сократить до того, что реально выполняется, и до чеклиста релиза.
- **Версия:** весь объём аудита A–E лежит в `Unreleased`, но сборки по-прежнему 3.7.3. Нужен релиз 3.8.0 с тегом.
- **Доступность:** не проводились проверка скринридером и аудит Lighthouse/axe на собранной странице. Не все интерактивные элементы проверены на размер 44×44 (кнопки дока и мелкие иконки виджетов).

**Вывод:** код в хорошем состоянии, но для публикации пока не готов, пока не закрыты P1–P6. Это 1–2 дня работы, что и составляет этап 0.

## 2. Целевая архитектура рабочего пространства

### 2.1. Ключевое ограничение

Расширение не может принимать входящие соединения: у него нет HTTP-сервера и открытого порта. Поэтому внешний агент не может «постучаться в расширение». Нужен посредник, а расширение подключается к нему само.

```text
 ┌──────────────── Браузер ────────────────┐        ┌──────── Локально / VPS ─────────┐
 │  New Tab (React)                         │        │  DashFlow Hub (демон)           │
 │   ├─ виджеты, Spaces, Command Palette    │        │   ├─ REST API  /v1/...          │
 │   └─ Domain services (items, boards…)    │◀─WS──▶ │   ├─ WebSocket (события)        │
 │  Service worker                          │        │   ├─ MCP-сервер (stdio/HTTP)    │
 │   ├─ Sync client (WS + повтор)           │        │   ├─ Коннекторы (RSS, GitHub,   │
 │   ├─ chrome.alarms → напоминания         │        │   │   Telegram, ICS, Todoist…)  │
 │   └─ RSS / fetch прокси                  │        │   ├─ Планировщик дайджестов     │
 │  IndexedDB — локальная копия (offline)   │        │   └─ SQLite + журнал аудита     │
 └──────────────────────────────────────────┘        └──────────┬──────────────────────┘
                                                                │ MCP / REST + токен
                                          ┌─────────────────────┼─────────────────────┐
                                     Hermes Agent          OpenClaw          Claude Code / n8n / cron
```

**Решение (предлагается ADR-017):** DashFlow Hub — отдельный лёгкий сервис (Node 22 / TypeScript, переиспользует типы из `src/core`) с хранилищем SQLite.
- Расширение остаётся полностью рабочим без Hub: offline-first, IndexedDB как источник для UI. Hub — опциональный источник и получатель данных.
- Агенты работают только с Hub: через MCP-инструменты или REST. В расширении у агентов нет кода и прав.
- Запуск: локально (`npx dashflow-hub`, автозапуск) или на VPS, если нужен доступ с нескольких устройств и агентов, работающих 24/7.

Отвергнутые альтернативы:
- **Native Messaging.** Нет порта, но нужна установка хоста в реестр под каждый браузер. Агенты всё равно не смогут подключиться напрямую, только через тот же процесс, так что сложность та же.
- **Только облачный backend.** Противоречит «локально и приватно» и добавляет счета за хостинг и требования GDPR.
- **Агент пишет в `chrome.storage` через внешнюю страницу (`externally_connectable`).** Требует открытой вкладки и не работает в фоне.

### 2.2. Единая модель данных: Item

Сейчас задачи, заметки и ссылки хранятся в отдельных ключах у каждого виджета (`dashflow_widget_todo_items_<id>`). Для дайджестов, досок и агентов этого мало, нужна общая сущность:

```ts
interface Item {
  id: string;                       // ULID: сортируемый, генерируется на клиенте и в Hub
  kind: 'task' | 'note' | 'reminder' | 'digest' | 'article' | 'link' | 'card';
  title: string;
  body?: string;                    // Markdown, рендер через санитайзер, без HTML/JS
  status?: string;                  // колонка доски: 'inbox' | 'todo' | 'doing' | 'done' | …
  boardId?: string;
  dueAt?: string; remindAt?: string; // ISO 8601 с часовым поясом
  tags: string[];
  source: { type: 'user' | 'agent' | 'connector'; id: string; name: string; url?: string };
  pinned?: boolean; archivedAt?: string; deletedAt?: string; // мягкое удаление
  createdAt: string; updatedAt: string; version: number;     // version для разрешения конфликтов
}
```

- **Синхронизация:** last-write-wins по `version` и `updatedAt` с журналом изменений `changes(seq)`. Клиент тянет изменения с курсора, CRDT не нужен.
- **Виджеты становятся представлениями над Item.** Todo — это `kind=task` без доски, Kanban — `kind=task|card` по `boardId`, Inbox — всё со `status=inbox`. Миграция: при первом запуске старые ключи превращаются в Items, старые ключи остаются ещё на одну версию для отката.
- **Источник истины:** для UI это IndexedDB, для синхронизации — Hub. Конфликт двух устройств разрешается по `version`, проигравшая версия сохраняется в `item_history`.

### 2.3. Безопасность API для агентов (модель угроз)

| Угроза | Мера |
|---|---|
| Чужой процесс на машине пишет в Hub | Hub слушает только `127.0.0.1`. Токены с областями действия (`items:read`, `items:write`, `boards:write`, `digests:write`) хранятся как SHA-256, сам токен показывается один раз при создании |
| Агент или коннектор пишет вредоносный контент (XSS) | Body — только Markdown, рендер через санитайзер с allowlist, ссылки только `http(s)`. Тот же принцип, что в `userContent.ts` |
| Prompt injection: статья из ленты приказывает агенту «удали все задачи» | По умолчанию агенты только добавляют и меняют свои записи (`source.id` = id агента). Удаление и правка чужих записей — отдельная область `items:manage`, по умолчанию выключена. Все операции агентов логируются и откатываются через «Отменить» в журнале |
| Флуд и раздувание хранилища | Rate limit на токен, лимиты размеров (как `USER_CONTENT_LIMITS`), квота записей на источник |
| Утечка содержимого | Чтение отдельно от записи. Агенту, который пишет дайджест, чтение задач не нужно |
| Hub на VPS | Только за HTTPS (Caddy). Токены отзываются, у каждого агента свой токен |

## 3. План по этапам

Приоритет оценён по соотношению пользы и трудозатрат. Каждый этап завершается рабочим результатом, который можно закоммитить, и записью в CHANGELOG.

### Этап 0 — Готовность к публикации (≈1–2 дня) — Must

1. P1/P2. Перевести `bookmarks`, `geolocation` и `https://*/*` в `optional_permissions` / `optional_host_permissions`. Запрашивать через `chrome.permissions.request` по жесту пользователя: при добавлении виджета закладок, при определении геолокации, при добавлении RSS или iframe с новым доменом. Связать с `PermissionConsentModal`. Обязательными остаются `storage` и хосты Open-Meteo, Unsplash и геокодера.
2. P3. `name: '__MSG_extensionName__'`, `description: '__MSG_extensionDescription__'`, `default_locale: 'en'` (магазинам нужен fallback).
3. P4. По `onUpdateAvailable` откладывать `reload()`, пока открыта вкладка DashFlow с несохранённым вводом. Либо показывать плашку «Доступно обновление — перезапустить».
4. P5. Типизированные сообщения воркера: discriminated union с проверкой формы. Редиректы через `redirect: 'manual'` с повторной проверкой каждого `Location`, максимум 3. Блок IPv6 ULA/link-local и нестандартной записи IPv4 через нормализацию `new URL().hostname`. Ответ ограничить 2 МБ, наружу отдавать код ошибки без деталей. Тесты на каждый вектор.
5. P6. `CHROMEWEBSTORE.md`: single purpose, обоснование прав, раскрытие использования данных, тексты листинга ru/en, список скриншотов.
6. CI: закрепить actions по SHA, Node 22, `npm audit --audit-level=high`, Dependabot, порог покрытия (зафиксировать текущий −2%), Playwright smoke на собранном расширении.
7. Документация: сократить SLO/MONITORING/BACKUP/DEPLOYMENT до реальных процессов, исправить COMPLIANCE и SECURITY по фактическому манифесту.
8. Релиз 3.8.0: перенести `Unreleased` в версию, поставить тег, собрать.

**Критерий готовности:** при установке не показывается предупреждение о доступе ко всем сайтам, smoke E2E в CI зелёный, документы совпадают с манифестом.

### Этап 1 — Фундамент рабочего пространства (≈1 неделя) — Must

1. Хранилище Item в IndexedDB (`items`, `boards`, `changes`) и доменный сервис `core/items` (CRUD, запросы, подписки) по аналогии с `core/storage`. Все виджеты меняют данные только через сервис.
2. Командная шина: `createItem`, `moveItem`, `completeTask`, `snooze` и т.д. Одни и те же команды вызывают UI, Command Palette и позже синхронизация с Hub. Отсюда отмена (undo) и журнал.
3. Spaces: несколько дашбордов («Работа», «Дом», «Утро») с переключением в доке и через `Ctrl+1…9`. Нынешний дашборд становится первым Space, миграция без потерь.
4. Миграция Todo, Notes и QuickLinks на Item, тесты миграции и отката. Экспорт 3.0 включает Items, импорт 2.x поддерживается.
5. Глобальный поиск по Items в Command Palette.

### Этап 2 — Виджеты рабочего пространства (≈1–2 недели) — Must/Should

| Виджет | Суть | Новые права |
|---|---|---|
| **Inbox** (Must) | Единая лента входящих: от агентов, коннекторов и быстрого ввода. Действия: в задачи, на доску, отложить, архивировать | — |
| **Kanban** (Must) | Доска по `boardId`, колонки настраиваются, drag-and-drop доступен с клавиатуры, WIP-лимиты | — |
| **Reminders** (Must) | `remindAt` → `chrome.alarms` → системное уведомление с действиями «Готово» и «+1 ч». Срабатывает и при закрытой вкладке | `alarms`, `notifications` (опционально) |
| **Digest** (Should) | Карточка дайджеста: заголовок, секции, ссылки на источники, «прочитано». Источник — агент или правило | — |
| **Feed Reader** (Should) | Развитие RSS: папки, непрочитанное, «прочитать позже» → Item, полнотекстовый просмотр в модальном окне | хосты по запросу |

### Этап 3 — DashFlow Hub и собственное API (≈1–2 недели) — Must для агентов

1. Пакет `hub/` в этом репозитории (npm workspaces): Node 22, Fastify, better-sqlite3, zod. Общие типы `Item` в `packages/shared`.
2. REST `/v1`: `items` (CRUD, фильтры, курсорная пагинация), `boards`, `digests`, `changes?since=`, `webhooks/incoming/:token`. Единый формат ошибок `{ error: { code, message } }` и `Idempotency-Key` на POST.
3. Спецификация OpenAPI 3.1 в `docs/API_ARCHITECTURE.md` и `hub/openapi.yaml`, клиент генерируется из неё.
4. WebSocket `/v1/stream`: события `item.created|updated|deleted`. Клиент в сервис-воркере с переподключением и экспоненциальной задержкой, офлайн-очередь команд.
5. Сопряжение: в настройках расширения «Подключить Hub», адрес и одноразовый код. Hub выдаёт токен устройства, токены агентов создаются в Hub CLI или в разделе настроек «Агенты».
6. Журнал аудита и отмена операций по источнику.

### Этап 4 — ИИ-агенты (≈1 неделя после этапа 3) — Must

1. MCP-сервер в Hub (stdio и Streamable HTTP). Инструменты: `list_items`, `search_items`, `create_item`, `update_item`, `complete_task`, `move_card`, `publish_digest`, `create_reminder`, `list_boards`. Ресурсы: `dashflow://inbox`, `dashflow://board/{id}`.
2. Подключение конкретных агентов (на этом шаге сверить актуальную документацию Hermes Agent и OpenClaw, допущение: оба умеют подключать MCP-серверы или вызывать HTTP-инструменты).
   - **Hermes Agent:** добавить MCP-сервер `dashflow-hub` в конфиг, cron-задача «утренний дайджест в 7:30 → `publish_digest`».
   - **OpenClaw:** skill `dashflow` (SKILL.md с описанием инструментов) поверх MCP или REST и ответы в мессенджере со ссылкой на Item.
   - **Claude Code и прочие MCP-клиенты** подключаются тем же сервером.
3. Обратное направление, из расширения к агенту. Команда «Поручить агенту» в Command Palette создаёт Item `kind=task` с `assignee=agent:<id>`, Hub отдаёт его агенту, агент отвечает комментарием или дайджестом. Для агентов без входящего канала это работает как очередь задач, которую агент опрашивает.
4. Готовые рецепты в `docs/agents/`: утренний дайджест (погода, календарь, ленты, GitHub), разбор Inbox, еженедельный обзор задач, «прочитать позже» → конспект.
5. UI: значок источника на каждой карточке (агент, коннектор, вы), фильтр по источнику, страница «Агенты» с токенами, областями действия, последней активностью и кнопками «Отозвать» и «Откатить последние N операций».

### Этап 5 — Интеграции (по одной, ≈1–2 дня каждая) — Should/Could

Коннекторы работают в Hub: секреты хранятся там, а не в расширении. Единый интерфейс `Connector { poll(): Item[]; push?(item) }` и расписание.

1. **Входящие webhooks.** Универсальный вход для n8n, Zapier, Make, IFTTT, GitHub, Home Assistant (Must, это дешёвая гибкость).
2. **GitHub.** Назначенные PR и issues, review requests → Inbox/Board.
3. **Telegram.** Бот для быстрого захвата в Inbox и пересылки напоминаний.
4. **Календарь:** ICS, позже Google Calendar OAuth.
5. **Todoist / Linear / Notion:** двусторонняя синхронизация задач (только по реальной необходимости).
6. **Email-дайджест:** IMAP, только заголовки и отправители, через правило.

### Этап 6 — Визуал и удобство (параллельно со 2–4) — Should

- Режимы плотности (Comfortable/Compact), «утренний экран» (Hero + Digest + Agenda), фокус-режим с одной доской.
- Быстрый захват: `Alt+N` из любой вкладки (команда расширения `commands`) и контекстное меню «Отправить в DashFlow» для выделенного текста или ссылки.
- Анимации перемещения карточек 150–200 мс с учётом `data-motion="reduced"`.
- Пустые состояния с подсказкой, что делать дальше. Онбординг с подключением Hub — по желанию.
- Проверка на 375 px, iPad, 13", FullHD, 4K. Аудит axe и проверка скринридером.

### Этап 7 — Оптимизация (по измерениям, правило 80) — Should

1. Замерить базовую линию: время до первого кадра новой вкладки (`WebVitalsMonitor`), размер чанков (`rollup-plugin-visualizer`), память на 20+ виджетах.
2. Бюджеты в CI: главный чанк ≤ 250 КБ gzip, LCP новой вкладки ≤ 300 мс на тёплом старте.
3. Кандидаты: ленивые модальные окна настроек и маркетплейса, виртуализация лент и Inbox (> 100 элементов), `lucide-react` по отдельным иконкам. Мгновенный первый кадр через снапшот раскладки в `localStorage` до гидратации IndexedDB.

## 4. Решения, которые нужно принять владельцу

1. **Где живёт Hub:** только локально (проще, данные не покидают машину) или VPS (агенты 24/7, несколько устройств). По умолчанию предлагается локально, VPS позже, код тот же.
2. **Публикация в магазинах:** если расширение только для себя, этап 0 сводится к безопасности (P4, P5), а P1/P2/P6 можно отложить. Если публикуем, этап 0 обязателен целиком.
3. **Hub в составе репозитория** (monorepo, предлагается) или отдельный репозиторий.
4. **Какие агенты первыми:** Hermes, OpenClaw или Claude Code. От этого зависят рецепты этапа 4.

## 5. Метрики успеха (для себя)

- Каждое утро открываю дашборд, и дайджест уже там: агент публикует его к 7:30 в ≥ 90% дней.
- Inbox разбирается до нуля минимум раз в день. Время от захвата до задачи — ≤ 2 действия.
- Ни одна запись не потеряна: миграции и синхронизация покрыты тестами, журнал позволяет откатить любую операцию агента.
- Новая вкладка открывается без заметной задержки (≤ 300 мс до контента).
