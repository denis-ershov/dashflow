# DashFlow: реструктуризация, редизайн и рефакторинг

- **Дата:** 2026-08-24
- **Статус:** дизайн согласован по секциям, ожидает вычитки спеки
- **Тип:** архитектурное изменение (полный процесс brainstorming → spec → plan)
- **Область:** `dashflow` — расширение Chrome MV3 на WXT, экран новой вкладки

## 1. Контекст и цель

DashFlow — новая вкладка с настраиваемым дашбордом: сетка виджетов, темы, каталог виджетов, задел под плагины. Кодовая база работает, но накопила расхождения между обещанным и фактическим: каталог дублирует реестр виджетов, слой плагинов существует как заглушка, адаптивность заявлена, но сетка одноколоночная по конфигурации, тестов нет ни одного, тексты интерфейса захардкожены по-русски.

Задача поставлена в два приоритета:

1. **Дизайн** — красивый, удобный, современный, адаптивный.
2. **Рефакторинг** — привести код в состояние, в котором дизайн можно поддерживать.

Целевая визуальная парадигма — гибрид референсов **HiTab** и **SuperStart**: обои во весь экран, виджет сам решает, есть ли у него рамка, плитки иконок с подписями как отдельный тип поверхности, боковой рельс управления, двухпанельные настройки.

### Что считается успехом

- Новая вкладка одинаково корректно выглядит от iPhone SE (375 px) до 4K без горизонтального скролла и наложений.
- Любая строка интерфейса приходит из локали; добавление языка не требует правки компонентов.
- Ни один упавший виджет не гасит дашборд.
- Схема хранилища меняется без потери раскладок существующих пользователей.
- Плагины и каталог работают по-настоящему, а не изображают работу.

## 2. Профили применимости (правило 114)

Активные профили:

- **Внутренний/клиентский инструмент без сервера.** Данные живут в браузере пользователя: `chrome.storage` и IndexedDB. Своего бэкенда нет, аккаунтов нет, multi-tenancy не применяется.
- **Расширение браузера, MV3.** Действует запрет на удалённо размещённый код, обязательна CSP страниц расширения, права из манифеста подлежат ревью в Chrome Web Store.
- **Публикуемый продукт с пользовательским контентом.** Пользователь вводит URL лент, адреса встраиваемых страниц, собственный CSS — всё это недоверенный ввод.

Профили, которые **не** активны и правила которых сознательно не применяются: платежи, регулируемые системы, SaaS/multi-tenant, AI-функции, публичный веб с SEO. Причина: расширение не имеет серверной части, не обрабатывает платежи и не индексируется поисковиками. SEO-правила (83) и правила AI (96–97) в этом изменении неприменимы.

## 3. Вне scope

Сознательно не входит в это изменение:

- синхронизация настроек между устройствами через аккаунт;
- загрузка плагинов из сети и публичный реестр плагинов;
- E2E-тесты и нагрузочное тестирование;
- поддержка Firefox и Safari (WXT это позволяет, но проверка выходит за рамки);
- RTL-локаль как поставляемый язык — архитектура её допускает, но перевод не добавляется;
- новые виджеты: работаем с уже существующими двенадцатью.

## 4. Секция 1. Целевая структура и слои

### 4.1. Принцип

Зависимости направлены строго в одну сторону: `shared` ← `services` ← `stores` ← `widgets` ← `shell` ← `entrypoints`. Слой не знает о слоях выше себя. Виджет не импортирует оболочку, оболочка не импортирует внутренности виджета, реестр не знает, кто его наполняет.

### 4.2. Структура каталогов

```
src/
  entrypoints/            обязательная конвенция WXT — точки входа
    newtab/               index.html, main.tsx, App.tsx
    background.ts
  shell/                  оболочка: рельс, слой обоев, хост модалок, режим правки
  widgets/
    core/                 реестр, контракты, WidgetShell, ErrorBoundary
    built-in/             12 встроенных виджетов, по папке на виджет
    declarative/          шаблоны декларативных плагинов
    sandbox/              мост в iframe-песочницу
  features/
    settings/             двухпанельные настройки
    catalog/              каталог виджетов и плагинов (бывший marketplace)
    themes/               выбор темы, обои, пользовательский CSS
    backup/               импорт и экспорт конфигурации
  stores/                 zustand-хранилища
  services/
    storage/              StorageAdapter, IndexedDB, миграции
    theme/                применение темы, валидация CSS
    i18n/                 локализация
    net/                  запросы наружу с таймаутами и лимитами
  shared/
    ui/                   кнопки, поля, модалка, drawer, скелетоны
    hooks/                переиспользуемые хуки
    lib/                  утилиты, валидаторы URL и схем
    styles/               tokens.css, globals.css
```

### 4.3. Что переезжает

| Сейчас | Становится | Почему |
| --- | --- | --- |
| `src/components/ui/` | `src/shared/ui/` | это не фича, а набор примитивов |
| `src/styles/` | `src/shared/styles/` | токены — часть общего слоя |
| `src/features/dashboard/components/GridEngine.tsx` | `src/shell/` + `src/widgets/core/` | сетка и оболочка — не фича, а каркас |
| `src/features/marketplace/` | `src/features/catalog/` | «marketplace» обещает магазин, которого нет |
| `src/plugins/rss-reader/` | `src/widgets/built-in/RssWidget/` | это встроенный виджет, а не плагин |
| `src/services/localization/` | `src/services/i18n/` | единое имя со остальным кодом |
| `docs/technical specifications.md` | `docs/TECHNICAL_SPECIFICATION.md` | пробел в имени нарушает конвенцию правила 3 |

### 4.4. Почему `src/plugins/rss-reader` перестаёт быть плагином

Файл импортируется статически из `src/widgets/built-in/index.ts:13` и регистрируется как обычный встроенный виджет, но в каталоге помечен `type: 'sdk'`. Это чистая фикция: никакой SDK его не загружает. Пока он лежит в `src/plugins/`, структура утверждает неправду о самой себе.

## 5. Секция 2. Дизайн-система и Theme Engine

### 5.1. Проблема

`src/styles/tokens.css` содержит 25 переменных, из которых тема реально переопределяет 7 — только цвета. Отступы, типографика, радиусы, тени, слои z-index живут в компонентах магическими числами: `text-[11px]`, `text-[9px]`, `w-3.5`, `rounded-xl`, `text-rose-400`. Правила 14 и 21 (единая дизайн-система, pixel perfect) на этом невыполнимы: каждый новый экран изобретает масштаб заново.

### 5.2. Контракт токенов

Токены делятся на три группы.

**Инварианты** — не зависят от темы, задаются один раз:

- Шаг сетки отступов кратен 4 px, имя токена равно множителю: `--space-1: 4px`, `--space-2: 8px`, `--space-3: 12px`, `--space-4: 16px`, `--space-5: 20px`, `--space-6: 24px`, `--space-8: 32px`, `--space-10: 40px`, `--space-12: 48px`.
- Типографика: `--text-xs: 12px`, `--text-sm: 13px`, `--text-base: 14px`, `--text-lg: 16px`, `--text-xl: 20px`, `--text-2xl: 24px`, `--text-3xl: 30px`, с парными `--leading-*`. Ниже 12 px текст не используется — сейчас в коде есть 9 px и 10 px, они нарушают правило 16.
- Радиусы: `--radius-sm: 8px`, `--radius-md: 12px`, `--radius-lg: 16px`, `--radius-xl: 20px`, `--radius-full: 999px`.
- Длительности: `--duration-fast: 150ms`, `--duration-base: 200ms`, `--duration-slow: 250ms` — коридор правила 19.
- Слои: `--z-base`, `--z-grid`, `--z-rail`, `--z-drawer`, `--z-modal`, `--z-toast`. Сейчас порядок наложения определяется случайными числами в классах.
- Минимальная цель нажатия: `--hit-min: 44px` (правило 16).

**Тема** — переопределяемая часть: фон, поверхность, поверхность при наведении, граница, текст, приглушённый текст, primary, secondary, accent, success, warning, danger, цвет фокусного контура, прозрачность и размытие стекла, интенсивность затемняющей подложки под обоями.

**Производные** — вычисляются из темы в CSS и не задаются пресетом вручную: цвет текста на primary, цвет границы стеклянной панели, цвет тени.

### 5.3. Применение темы

Тема применяется одним тегом `<style id="dashflow-theme">`, содержащим единственный блок `:root { … }`. Одна операция вместо десятков `setProperty`, атомарное переключение без промежуточных кадров, и тот же механизм принимает пользовательский CSS.

Порядок каскада фиксирован: базовые токены из `tokens.css` → блок активного пресета → пользовательские переопределения → пользовательский CSS. Пользователь всегда может испортить себе внешний вид — но никогда безвозвратно: кнопка сброса к пресету доступна из настроек и не зависит от того, отрисовался ли интерфейс.

### 5.4. Пресеты

- **Neutral Dark** — по умолчанию: `#0b0f17` фон, `#3b82f6` primary, `#06b6d4` secondary, `#8b5cf6` accent. Это то, что уже лежит в `tokens.css`; выбор сохраняет привычный вид у существующих пользователей.
- **Deep Blue** — синяя гамма из ТЗ (`#12232E`, `#203647`, `#007CC7`, `#4DA8DA`), сохранена как пресет, а не как значение по умолчанию.
- **Glass** — усиленное стекло, рассчитано на обои.
- **High Contrast** — тёмный без прозрачности, контраст выше AA, для доступности.
- **Light** — светлая тема.

### 5.5. Обои

Источник обоев: URL или локальный файл. Разрешённые схемы — `https:`, `data:`, `chrome-extension:`; всё остальное отклоняется с понятной ошибкой. Локальный файл кладётся в IndexedDB, а не в `chrome.storage`: квота `chrome.storage.local` кончится на первой же фотографии.

Между обоями и контентом обязательно лежит регулируемая затемняющая подложка (scrim). Это не декор, а требование доступности: без неё контраст текста на стеклянной панели поверх светлого снимка падает ниже 4.5:1. Контраст проверяется в двух условиях — на чистом фоне темы и на стекле поверх обоев.

### 5.6. Пользовательский CSS

Пользовательский CSS — недоверенный ввод и валидируется до попадания в DOM:

- парсинг через конструируемый `CSSStyleSheet` в `try/catch`: не разобралось — не применяется, пользователь видит ошибку;
- `@import` запрещён полностью;
- `url()` допускает только `data:` и `chrome-extension:`;
- ограничение по размеру;
- отдельный выключенный по умолчанию тумблер для внешних ресурсов.

Причина запретов: `@import` и произвольный `url()` — это исходящий сетевой запрос с IP пользователя и фактом открытия вкладки, то есть утечка, а не оформление.

## 6. Секция 3. Layout Engine и оболочка

### 6.1. Оболочка: вариант A

Постоянно видимый левый рельс иконок. На узких экранах (< 600 px) рельс превращается в нижнюю панель — там, где до него дотягивается большой палец.

```
┌──┬────────────────────────────────────┐
│  │                                    │
│ ▢│        обои + сетка виджетов       │
│ ▢│                                    │
│ ▢│                                    │
│ ▢│                                    │
│ ⚙│                                    │
└──┴────────────────────────────────────┘
```

Рельс содержит: правку раскладки, каталог, темы, настройки. Каждая цель нажатия — не меньше 44×44, каждая имеет `aria-label` из локали (сейчас в `WidgetCard` вместо этого стоит русский `title=`).

Контейнер сетки лишается `max-w-7xl`: на 4K это оставляло дашборд узкой полосой посередине при пустых боках.

### 6.2. Адаптивная сетка

`ResponsiveGridLayout` из `react-grid-layout` используется по назначению, с типизированным `WidthProvider` вместо двух приведений `as any` в текущем `GridEngine.tsx`.

| Breakpoint | Ширина | Колонок |
| --- | --- | --- |
| `xxs` | < 360 px | 2 |
| `xs` | 360–599 px | 4 |
| `sm` | 600–899 px | 6 |
| `md` | 900–1199 px | 8 |
| `lg` | 1200–1599 px | 12 |
| `xl` | ≥ 1600 px | 12 |

iPhone SE (375 px) попадает в `xs` — четыре колонки, как в согласованном макете. Ниже двух колонок не опускаемся никогда: одна колонка превращает дашборд в список.

Высота строки не фиксируется на `90px`, как сейчас, а вычисляется так, чтобы клетка была близка к квадрату, с ограничением в коридоре 72–140 px. Иначе виджет 2×2 на 4K выглядит приплюснутым, а на мобильном — вытянутым.

Раскладка хранится по breakpoint отдельно и заполняется лениво: пользователь, который переставил виджеты на ноутбуке, не должен потерять расстановку, открыв вкладку на внешнем мониторе. Незаполненный breakpoint наследуется от ближайшего заполненного при первом показе, дальше живёт своей жизнью.

`minSize` из определения виджета наконец соблюдается: сейчас `GridEngine` подставляет `minW: 1, minH: 1` всем подряд, из-за чего виджет можно сжать до нечитаемого состояния.

### 6.3. Три типа поверхности

Ключевое решение редизайна: рамку выбирает виджет, а не оболочка. `WidgetShell` (бывший `WidgetCard`) читает поле `surface` из определения виджета:

- **`chromeless`** — без панели и фона, элемент лежит прямо на обоях. Так работают часы и цитата: панель вокруг цифр — визуальный шум.
- **`panel`** — стеклянная панель с заголовком. Для содержимого со списками и прокруткой: задачи, заметки, лента, погода.
- **`tiles`** — плитки иконок с подписями, собственная внутренняя сетка. Для быстрых ссылок и закладок; это отдельный тип, а не панель со списком внутри.

Заголовок и кнопки управления не висят постоянно, как сейчас, а появляются при наведении и при фокусе с клавиатуры. Появление по фокусу обязательно: иначе управление недоступно без мыши.

### 6.4. Правка раскладки как отдельный режим

Перетаскивание и изменение размера включены только в режиме правки. В обычном режиме виджеты не сдвигаются от случайного промаха, а выделение текста в заметках не превращается в перетаскивание.

В режиме правки доступна клавиатура: стрелки перемещают выбранный виджет по сетке, `Shift` + стрелки меняют размер, `Escape` выходит. `react-grid-layout` клавиатурного драга не даёт — для плиток внутри поверхности `tiles` берётся `@dnd-kit/sortable` (~10 КБ), у которого он есть. Это единственная новая зависимость в разделе UI, и она добавляется ради доступности, а не удобства реализации.

## 7. Секция 4. Контракты и типы

### 7.1. Проблема

Типы описывают не то, что происходит на самом деле. `settings?: Record<string, any>` в `useDashboardStore` — это `any` в самом центре модели данных (нарушение правила 33). Названия и описания виджетов лежат в реестре русскими строками, что делает i18n невозможной без переписывания реестра. `ActiveModal` содержит вариант `'add'`, который никто не открывает. `initializeDashboard` — пустая функция, которую `App.tsx` продолжает вызывать.

### 7.2. Определение виджета

Определение виджета описывает виджет, а не его перевод:

- `id`, `version`, `category`, `iconName`;
- `titleKey`, `descriptionKey` — ключи локали вместо готовых строк;
- `defaultSize`, `minSize`, опционально `maxSize`;
- `surface` — `chromeless` | `panel` | `tiles` (секция 3);
- `settingsSchema` — схема настроек, где `labelKey` тоже ключ;
- `permissions` — реальные права, а не украшение;
- `load` — `() => Promise<ComponentType>` для ленивой загрузки.

Ленивая загрузка через `React.lazy` — это и есть недостающее разделение бандла (правило 17). Сейчас все двенадцать виджетов попадают в один чанк новой вкладки, даже если пользователь добавил один.

### 7.3. Типобезопасные настройки

`settingsSchema` перестаёт быть просто описанием формы и становится источником типа. Настройки виджета выводятся из его схемы, а не объявляются вторым, независимым типом, который со временем разъезжается с формой. Значения из хранилища проходят валидацию по схеме при чтении: файл конфигурации, импортированный пользователем, — недоверенный ввод, а не гарантированно валидный объект.

Неизвестное поле в настройках отбрасывается, поле неверного типа заменяется значением по умолчанию, пользователь видит уведомление. Молчаливое падение виджета из-за чужого конфига недопустимо.

### 7.4. Реестр

Реестр остаётся единственным источником истины о виджетах. Каталог его читает, а не дублирует (сейчас `CATALOG_ITEMS` — вторая копия данных, где `rssReader` имеет версию 1.1.0 против 1.0.0 в реестре). Реестр не знает, кто его наполняет: встроенные виджеты и декларативные плагины регистрируются одинаково.

Регистрация переезжает из `useEffect` в `GridEngine` в явную инициализацию до первого рендера. Регистрация в эффекте означает, что первый кадр рисуется по пустому реестру.

### 7.5. Хранилище и миграции

Текущий `persist` объявлен как `name: 'dashflow_dashboard_store'` без `version` и без `migrate`. Любое изменение формы состояния — и раскладки существующих пользователей превращаются в мусор молча. Это прямое нарушение правил 51 и 102.

Вводится версионированная схема: номер версии, цепочка миграций «из версии N в N+1», проверка результата после каждого шага. Перед миграцией делается резервная копия предыдущего состояния; если миграция бросила исключение, применяется копия и пользователь видит сообщение, а не пустой дашборд. Первая миграция — из текущего безверсионного состояния в версию 1, включая перенос раскладки в формат «по breakpoint» из секции 3.

Идентификаторы экземпляров перестают строиться на `Date.now()`: два виджета, добавленные в одну миллисекунду, получают одинаковый ключ. Используется `crypto.randomUUID()`.

Размещение нового виджета перестаёт вычисляться как `(state.widgets.length * 4) % state.columns` — эта формула кладёт виджет поверх существующего, как только в раскладке появляются дырки. Ищется первое свободное место, подходящее по размеру.

### 7.6. Локализация

Локали — плоские JSON-словари по неймспейсам (`common`, `widgets`, `settings`, `catalog`, `errors`). Ключи стабильные и семантические; текст интерфейса ключом не является (правило 43.1).

Поставляются `ru` (основной) и `en` (fallback). Порядок определения языка: явный выбор пользователя → `chrome.i18n.getUILanguage()` → `ru`. Отсутствующий ключ приводит к fallback-языку, затем — к самому ключу, но никогда к `undefined` или пустой строке на экране.

Собственный минимальный слой i18n вместо `i18next`: расширению нужны подстановка параметров, множественное число через `Intl.PluralRules` и fallback. `i18next` весит около 40 КБ и приносит функциональность, которая здесь не используется (правило 41).

Даты, числа и относительное время форматируются через `Intl.*`, а не вручную. Сейчас `RssWidget` зовёт `toLocaleTimeString`, а остальные виджеты форматируют по-своему.

## 8. Секция 5. Плагины, каталог и безопасность

### 8.1. Что происходит сейчас

`PluginHost` рисует iframe с `srcDoc`, внутри которого написано «Запущен в изолированной песочнице». Никакого плагина там нет: проп `scriptUrl` не используется, а сам компонент вызывается только когда `WidgetRegistry.get()` вернул `undefined` — то есть никогда, потому что все двенадцать виджетов зарегистрированы как встроенные. Слой плагинов существует как декорация.

### 8.2. Декларативные плагины

MV3 запрещает удалённо размещённый код, но запрет «не распространяется на данные, такие как JSON или CSS». Отсюда модель: плагин — это JSON-манифест без кода, который параметризует один из четырёх встроенных шаблонов:

1. **RSS-источник** — набор лент с настройками отображения.
2. **Встраиваемая страница** — адрес и параметры iframe.
3. **Набор ссылок** — плитки с иконками и подписями.
4. **API-виджет** — запрос к JSON-эндпоинту и декларативное сопоставление полей с шаблоном отображения.

Манифест проходит ту же валидацию по схеме, что и настройки виджета (секция 4). Источники в MVP — импорт файла и ручной ввод; загрузки из сети нет.

Такой плагин честно назвать плагином: он расширяет дашборд без пересборки расширения и при этом законен под MV3.

### 8.3. Песочница и мост сообщений

`PluginHost` переписывается. Путь «виджет не найден» превращается в состояние «виджет недоступен» из секции 4 — с именем виджета и кнопкой удаления, а не в фальшивую песочницу.

iframe получает `sandbox="allow-scripts"` без `allow-same-origin`. Последствие семантики: origin такого фрейма — `null`, поэтому ответы отправляются с `targetOrigin: 'null'`, а отправитель определяется сравнением `event.source === iframe.contentWindow` — по идентичности окна, а не по строке origin. Проверка origin здесь бессмысленна: `'null'` одинаков у всех песочниц.

Один слушатель уровня приложения вместо слушателя на каждый экземпляр. Сейчас любой фрейм может записать в пространство ключей любого плагина, потому что слушатели не различают отправителей.

Мост даёт ограниченный набор операций: чтение и запись собственных настроек, запрос данных через сервис сети, уведомление о размере. Каждая операция проверяет, что вызывающий фрейм имеет соответствующее право.

### 8.4. Права как реальный механизм

Сейчас `permissions` — строка текста в карточке каталога. Становится механизмом:

- при установке показывается экран согласия с понятным описанием последствий (правило 112);
- согласие хранится вместе с версией манифеста; расширение набора прав в новой версии требует повторного согласия;
- право отзывается из настроек;
- проверка происходит в точке доступа к данным, а не только в интерфейсе.

`host_permissions: ['<all_urls>']` в манифесте сужается: адреса пользовательских лент переезжают в `optional_host_permissions` и запрашиваются в момент добавления ленты. Для страниц расширения и песочницы задаётся явный `content_security_policy`.

### 8.5. Конкретные исправления безопасности

**`IframeWidget`** (`src/widgets/built-in/IframeWidget/IframeWidget.tsx:36`) — `allow-same-origin` убирается: вместе с `allow-scripts` эта пара снимает изоляцию песочницы. URL ограничивается схемой `https:` и валидируется перед подстановкой; сейчас значение берётся из настроек без проверки, а настройки приходят в том числе из импортированного файла. Неиспользуемый импорт `RefreshCw` удаляется (правило 28).

**`RssWidget`** (`src/plugins/rss-reader/RssWidget.tsx`):

- ссылка из ленты проверяется на схему до попадания в `href` — иначе `javascript:` из недоверенной ленты выполняется по клику;
- картинки из лент грузятся только с явного согласия: запрос за картинкой отдаёт стороннему серверу IP пользователя и время открытия вкладки;
- публичный CORS-прокси `api.allorigins.win` (строка 61) перестаёт быть автоматическим запасным вариантом — сейчас список лент пользователя молча уходит третьей стороне. Прокси становится явно включаемой опцией с предупреждением;
- фоновый запрос получает таймаут и ограничение размера ответа; сейчас ни того, ни другого нет;
- `chrome.runtime.lastError` проверяется, `any` в ответе заменяется типом;
- добавляется состояние ошибки: если все ленты не загрузились, сейчас рисуется пустой список без объяснения (нарушение правила 18);
- количество элементов на ленту перестаёт быть захардкоженной пятёркой и переезжает в настройки;
- комментарий «Сортировка новостей по дате или вперемешку» удаляется вместе с ложным утверждением — сортировка либо реализуется, либо не обещается.

### 8.6. Каталог

`CATALOG_ITEMS` перестаёт быть массивом в компоненте с JSX-иконками внутри данных. Каталог собирается из реестра: имя, описание и версия берутся оттуда, поэтому расхождение версий становится невозможным по построению.

Добавляются поиск и фильтр по категориям с ключами локали вместо английских строк `['All', 'News', 'Utilities', …]`, состояния загрузки, пустого результата и ошибки (правило 18). Удаление перестаёт снимать первый попавшийся экземпляр: при нескольких экземплярах виджета пользователь выбирает, какой удалить, и подтверждает действие.

## 9. Секция 6. Качество, проверки и документация

### 9.1. Факты на входе

Проверено в текущем состоянии репозитория:

- `ErrorBoundary` и `componentDidCatch` не встречаются в `src` ни разу — падение любого виджета гасит весь дашборд;
- `aria-` и `role=` встречаются четыре раза во всём проекте: три в `src/components/ui/Modal.tsx`, один в `src/components/ui/Drawer.tsx`;
- тестовых файлов нет ни одного, при этом `npm test` — это `vitest run`, который завершается успешно; зелёный статус ничего не значит;
- `vitest.config.ts:11` задаёт `environment: 'node'` — тестировать React-компоненты в такой конфигурации невозможно;
- ESLint и Prettier в `package.json` отсутствуют;
- каталога `.github` нет, CI нет;
- `@types/react-grid-layout` лежит в `dependencies` вместо `devDependencies`.

### 9.2. Устойчивость к ошибкам

`ErrorBoundary` встраивается в `WidgetShell`: упавший виджет показывает на своём месте сообщение и кнопку перезагрузки, остальной дашборд продолжает работать. Второй `ErrorBoundary` — на корне приложения, как последняя линия.

Логируется факт ошибки, идентификатор виджета и стек, но **не содержимое настроек**: там лежат личные URL, города и списки лент (правило 35).

### 9.3. Доступность

Помимо того, что уже покрыто секциями 2 и 3 (контраст, цели 44×44, появление управления по фокусу, клавиатурная правка раскладки):

- фокус запирается внутри модалок и drawer и возвращается на вызвавший элемент при закрытии;
- `Escape` закрывает любой оверлей;
- асинхронные обновления (загрузка ленты, погоды, установка виджета) сопровождаются `aria-live`;
- `prefers-reduced-motion` отключает анимации;
- перед завершением проводится проход только с клавиатуры и одна проверка скринридером.

### 9.4. Тесты

`environment` меняется на `jsdom`, добавляются `jsdom` и `@testing-library/react`. Пирамида (правило 62) для расширения без бэкенда выглядит так.

**Обязательные unit-тесты** — там, где ошибка молча портит данные пользователя:

- миграции хранилища, включая переход из безверсионного состояния;
- валидатор настроек и валидатор манифеста плагина;
- валидатор пользовательского CSS;
- проверка схем URL (ленты, встраиваемые страницы, ссылки из лент);
- вычисление числа колонок и высоты строки по ширине;
- вывод строк локали: подстановка, множественное число, fallback.

**Компонентные тесты** — состояния из правила 18 для виджетов с асинхронными данными: загрузка, пусто, ошибка, успех, нет прав.

**Негативные тесты безопасности** — обязательны:

- сообщение из чужого окна отклоняется мостом;
- `javascript:`-ссылка из ленты не доходит до `href`;
- плагин без согласия на право не получает доступ к хранилищу.

E2E вне scope (раздел 3).

### 9.5. Линтер и CI

Добавляются ESLint (TypeScript, React, hooks, jsx-a11y) и Prettier. Конвейер CI (правило 65):

```
lint → tsc --noEmit → vitest run → wxt build
```

Красный конвейер блокирует merge. `@types/react-grid-layout` переезжает в `devDependencies`.

### 9.6. Документация

Все восемь файлов в `docs/` приводятся в соответствие с кодом (правила 3–7):

| Документ | Что делаем |
| --- | --- |
| `PLUGIN_SDK_ARCHITECTURE.md` | переписывается под декларативную модель вместо загрузки скриптов |

### 9.7. ADR к созданию

- **ADR-001. Декларативные плагины вместо загрузки кода** — потому что MV3 запрещает удалённо размещённый код, а JSON под запрет не попадает.
- **ADR-002. `react-grid-layout` вместо собственной сетки** — зависимость уже в проекте, поведение перетаскивания и коллизий писать заново дороже, чем типизировать `WidthProvider`.
- **ADR-003. Neutral Dark по умолчанию, синяя гамма ТЗ как пресет** — сохраняет привычный вид существующих пользователей, не теряя гамму из ТЗ.
- **ADR-004. Собственный слой i18n вместо `i18next`** — нужны три возможности из многих, вес 40 КБ не оправдан.
- **ADR-005. `@dnd-kit/sortable` для плиток** — единственная причина: клавиатурное перетаскивание, которого нет в `react-grid-layout`.

## 10. Миграции и откат

Изменение затрагивает форму хранимых данных, поэтому обязательны и миграция, и откат (правила 42, 51, 73).

**Миграция.** Версия 0 (текущее состояние без `version`) → версия 1: раскладка переносится в формат «по breakpoint», `settings` валидируются по схемам, неизвестные виджеты помечаются как недоступные вместо удаления, идентификаторы экземпляров сохраняются как есть (перегенерация ломает связь с настройками).

**Резервная копия.** Перед миграцией исходное состояние сохраняется под отдельным ключом. Копия живёт до следующей успешной миграции.

**Откат.** Установка предыдущей версии расширения читает резервную копию и продолжает работать со старой схемой. Поэтому копия хранится в формате версии 0, а не в промежуточном виде.

**Экспорт и импорт.** Пользователь может выгрузить конфигурацию файлом и загрузить обратно — это и ручной откат, и путь миграции между профилями браузера. Импортируемый файл проходит полную валидацию как недоверенный ввод.

## 11. Этапы работ

Стратегия «фундамент → слои». После каждого этапа проект собирается и работает — это условие, а не пожелание.

| Этап | Содержание | Признак завершения |
| --- | --- | --- |
| 1 | Токены, тема, `<style id="dashflow-theme">`, пресеты, валидация CSS | сборка зелёная, старый интерфейс выглядит как раньше |
| 2 | Контракты, типы, локали, версионированное хранилище с миграцией | миграция покрыта тестами, раскладка существующего пользователя цела |
| 3 | Оболочка (рельс), адаптивная сетка, `WidgetShell` с тремя поверхностями, `ErrorBoundary`, режим правки | проверено на 375 / 768 / 1440 / 3840 px |
| 4 | Виджеты по одному: ленивая загрузка, ключи локали, `minSize`, состояния правила 18 | каждый виджет проходит свой чек-лист состояний |
| 5 | Декларативные плагины, песочница, права с согласием, каталог из реестра, исправления безопасности | негативные тесты безопасности зелёные |
| 6 | Линтер, Prettier, тесты, CI, документация, ADR, CHANGELOG | конвейер `lint → typecheck → test → build` зелёный |

Порядок именно такой: виджеты нельзя чинить до контрактов, контракты бессмысленны без токенов, а тесты и документация фиксируют то, что уже существует.

## 13. Риски и открытые вопросы

- **Объём.** Шесть этапов затрагивают почти весь `src`. Митигация — требование работоспособной сборки после каждого этапа и отдельная запись в CHANGELOG на этап.
- **Ленивая загрузка виджетов** даёт кадр со скелетоном там, где раньше содержимое появлялось сразу. Скелетон должен занимать ровно место виджета, иначе сетка дёргается.
- **Отказ от `allow-same-origin`** может сломать часть встраиваемых страниц. Это осознанная плата за изоляцию; в интерфейсе появляется явное сообщение, если страница отказалась встраиваться.
- **`prefers-color-scheme`.** Нужно ли переключать светлую и тёмную темы автоматически по системной настройке или оставить выбор полностью за пользователем — решается на этапе 1.
- **Сортировка лент.** Смешивать элементы разных лент по дате или группировать по источнику — решается на этапе 4 при разборе `RssWidget`.
