# Реструктуризация, редизайн и рефакторинг DashFlow

- **Дата:** 2026-08-24
- **Статус:** на вычитке у владельца продукта
- **Класс изменения:** архитектурное — меняются структура слоёв, контракты виджетов, формат хранимых данных и контур безопасности
- **Основание:** правила 45 (требования), 47 (scope control), 49 (ADR), 108 (Definition of Ready), 114 (профили)

Документ фиксирует согласованный дизайн. Он не является планом реализации: план создаётся отдельно после вычитки этой спеки.

## 1. Задача и ценность

DashFlow — расширение Chrome (Manifest V3) на WXT, заменяющее новую вкладку персональным дашбордом. Текущее состояние: 4841 строка в `src/`, 12 встроенных виджетов, рабочая сетка на `react-grid-layout`, темы, импорт/экспорт настроек.

**Проблема.** Продукт выглядит и ведёт себя как административная панель, а не как персональная стартовая страница: каждый виджет обёрнут одинаковой карточкой со стеклом, рамкой и постоянно видимой шапкой, поэтому часы и поиск неотличимы от таблицы закладок. Одновременно накопился технический долг, который блокирует развитие: мультиязычность невозможна (имена виджетов — строки в коде), код-сплиттинга нет (все 12 виджетов грузятся на первом экране), типизация настроек отсутствует (`any`), слой плагинов существует только в виде заглушки, тестов и линтера нет, восемь документов в `docs/` расходятся с кодом.

**Ценность.** Пользователь получает тихую, красивую и адаптивную новую вкладку, которая одинаково работает от iPhone SE до 4K, открывается быстро и не падает целиком из-за одного виджета. Команда получает границы слоёв, проверяемые контракты и зелёный CI, после которых новая функция не требует правок в пяти несвязанных местах.

**Приоритеты, заданные заказчиком:** первый — красивый, удобный, современный и адаптивный дизайн; второй — рефакторинг кода. Порядок работ ниже это отражает: визуальный слой становится рабочим раньше инфраструктурных улучшений, но не за счёт целостности данных.

## 2. Профили применимости (правило 114)

| Профиль | Активен | Следствия для этой работы |
|---|---|---|
| Внутренний инструмент / персональное расширение | да | доступ по умолчанию закрытый, требования безопасности и восстановления сохраняются |
| Публичный веб-продукт | нет | SEO, Open Graph, sitemap, hreflang, Core Web Vitals неприменимы: страница новой вкладки не индексируется |
| SaaS / multi-tenant | нет | нет организаций, ролей, квот и биллинга; multi-tenancy архитектурно не закладывается |
| Мобильное приложение | нет | нет store review и push; при этом Mobile First из правила 8 остаётся обязательным как требование к вёрстке |
| AI-функции | нет | правила 96–97 неприменимы |
| Платежи | нет | правила идемпотентности платежей неприменимы |
| Регулируемая система | нет | формальные SLO и независимый аудит не требуются |

Дополнительный профиль, специфичный для проекта: **браузерное расширение MV3**. Из него следуют жёсткие ограничения, которые определяют несколько решений ниже: запрет удалённо размещённого кода, обязательный `content_security_policy`, квоты `chrome.storage`, невозможность обойти политику расширений «своим загрузчиком плагинов».

Персональные данные обрабатываются в минимальном объёме и **не покидают устройство**: закладки, задачи, заметки, города погоды, адреса лент. Серверной части у продукта нет, поэтому GDPR-контур ограничен правилами хранения и удаления локальных данных (раздел 12).

## 3. Границы работ

### Входит

1. Новая структура каталогов и правила границ между слоями.
2. Дизайн-система: шкалы отступов, типографики, радиусов, теней, z-index, таймингов; новый контракт темы; конструктор тем; обои со скримом; валидация пользовательского CSS.
3. Оболочка новой вкладки: левый рельс, двухпанельные настройки, три типа поверхностей виджета, адаптивная сетка, режим правки, клавиатурная работа.
4. Контракты: типизированное определение виджета, ленивая загрузка, схема настроек как форма и как валидатор, версионирование и миграция хранилища, полноценный i18n.
5. Плагины: декларативная модель, переписанная песочница, экран согласия на права, каталог из единого источника правды.
6. Безопасность: схемы URL, CSP, сужение host permissions, RSS-конвейер, модель угроз в документации.
7. Качество: границы ошибок, доступность, тесты, ESLint, Prettier, CI, приведение документации в соответствие с кодом.

### Не входит сознательно (правило 47)

- **Загрузка плагинов с сервера и публичный Marketplace-бэкенд.** Каталог остаётся локальным; установка — из встроенного списка или из файла манифеста. Причина: сервера у продукта нет, а его появление — отдельный проект со своими требованиями к модерации и подписи.
- **E2E-тесты.** В этот заход не входят; обоснование в разделе 10.
- **Синхронизация дашборда между устройствами.** В `chrome.storage.sync` уходят только язык и выбранная тема: раскладка и настройки виджетов физически не проходят по квоте.
- **Firefox и Safari.** Целевой браузер — Chrome; WXT позволяет добавить сборку под другой браузер позже, но кросс-браузерная проверка в объём не входит.
- **Новые виджеты.** Работаем с существующими двенадцатью. Исключение — шаблонные компоненты для декларативных плагинов, без которых плагины неработоспособны.
- **Смена сеточной библиотеки.** `react-grid-layout` остаётся (ADR-002).
- **Отказ от Tailwind в пользу CSS-модулей или наоборот.** Текущая связка Tailwind 4 + CSS-переменные сохраняется.

## 5. Секция 1. Структура проекта и границы слоёв

### Целевая структура

```
src/
  entrypoints/          конвенция WXT — background.ts, newtab/ (только точка входа)
  core/                 ядро; о конкретных виджетах не знает ничего
    config/             feature flags, брейкпоинты, константы
    errors/             AppError, ErrorBoundary, нормализация
    i18n/               движок, локали, Intl-форматтеры, хуки
    storage/            адаптер, типизированный реестр ключей, миграции
    theme/              токены ↔ тема, применение, валидация custom CSS
    widget/             контракт, реестр, генератор форм настроек
    plugin/             манифест, валидация, permission-контур, sandbox host
  ui/                   дизайн-система; о домене не знает ничего
    primitives/         Button, Input, Select, Switch, Slider, Tooltip, Badge
    overlays/           Modal, Drawer, Dropdown, Popover, Toast
    layout/             Stack, Section, Surface, Rail
    feedback/           Skeleton, EmptyState, ErrorState, Spinner
  features/             склейка ui + core в продуктовые сценарии
    dashboard/          shell, поверхности, тулбар, командная палитра
    settings/           двухпанельная модалка и её разделы
    appearance/         темы, фоны, конструктор, CSS-редактор
    catalog/            единый каталог: Marketplace + добавление виджета
    backup/             импорт/экспорт JSON
  widgets/              12 самодостаточных папок + ленивый реестр манифестов
  styles/               tokens.css, globals.css
tests/                  unit/, component/
```

### Правила границ

Проверяются на код-ревью и являются частью Definition of Done каждого этапа:

- `core/` импортирует только `core/`.
- `ui/` знает про токены и хук i18n, но не про домен и не про виджеты.
- `widgets/*` берут контракт из `core/widget` и компоненты из `ui/`, но **никогда друг друга**.
- `features/` — единственный слой, которому разрешено склеивать всё.

### Что чинится этой структурой

- `src/plugins/rss-reader/` растворяется в `widgets/rss/` — протечка границы исчезает.
- `sdk/` переезжает в `core/plugin/` рядом с валидацией манифеста: контракт и его проверка лежат вместе.
- Двойная конвенция состояния уходит: стор живёт рядом с владельцем (`core/theme/themeStore.ts`, `features/dashboard/dashboardStore.ts`), а не в общей свалке.
- `registerBuiltInWidgets()` на 230 строк распадается на 12 манифестов по папкам плюс тонкий ленивый реестр.
- `BookmarksWidget.tsx` на 323 строки делится на контейнер, три представления и хук навигации по папкам; там же уходит `<table>`, запрещённая правилом 10 на узких экранах.
- Появляется `docs/adr/` (правило 49) — перечень ADR в разделе 15.

## 6. Секция 2. Дизайн-система и Theme Engine

### Один источник правды вместо трёх

Разделяется то, что сейчас смешано:

- **`tokens.css` держит структуру** — шкалы, которые тема не меняет: отступы, типографическая шкала, радиусы, тени, z-index, тайминги.
- **Тема держит значения** — цвета, стекло, радиус-пресет, шрифт и масштаб.

Новые шкалы задаются явно, чтобы «на глаз» стало невозможно:

| Шкала | Значения |
|---|---|
| Отступы | 2, 4, 8, 12, 16, 24, 32, 48, 64 px |
| Типографика | 12, 13, 14, 16, 20, 24, 32, 48, 64 px с фиксированными межстрочными |
| Радиусы | наследуются из текущих `xs`–`full`, выбор задаётся пресетом темы |
| z-index | `base 0`, `raised 10`, `grid-item-active 20`, `rail 30`, `overlay 40`, `modal 50`, `toast 60` |
| Тайминги | 150 / 200 / 250 ms (правило 19 — верхняя граница 250 ms) |

Магические `z-40` и `z-index: 100` заменяются на токены из этой шкалы.

### Применение темы

Вместо записи в `documentElement.style` — один тег `<style id="dashflow-theme">` с блоком `:root { … }`. Специфичность та же, но порядок каскада предсказуем, внутри можно держать условные токены под `prefers-contrast` и `prefers-reduced-motion`, а сброс — это `textContent = ''`. Пользовательский CSS идёт вторым тегом, строго после темы. Блок `[data-theme='light']` из `tokens.css` перестаёт молча перебиваться инлайновыми стилями.

### Контракт темы

Расширяется ровно настолько, насколько нужно:

- **Цвета** — к текущим семи добавляются `surfaceActive`, `primaryFg`, `borderHover` и семантические `danger / warning / success / info`. Последние закрывают дыру с захардкоженными `text-rose-400` и `text-emerald-400`.
- **Стекло** — `blur` и `opacity` как настраиваемые токены: это ядро визуала, и на светлых обоях нужны другие значения, чем на тёмных.
- **Радиус** — один пресет (как «Shape» в HiTab), а не восемь отдельных ручек.
- **Типографика** — семейство шрифта плюс масштаб; масштаб нужен по правилу 16 и для 4K.

Тени и тайминги в UI настроек **не выносятся** — они выводятся из режима темы. Осознанный YAGNI: восемь ручек для теней никто не использует, а конструктор от них становится нечитаемым.

Все токены темы применяются целиком: расхождения «выбрал Ocean Teal, а свечения остались синими» после этого быть не может — приёмка проверяет отсутствие цветов вне палитры.

### Палитра по умолчанию и пресеты

Палитра по умолчанию — **нейтральная тёмная**, то есть текущие значения `tokens.css`: `#0b0f17` фон, `#3b82f6` primary, `#06b6d4` secondary, `#8b5cf6` accent. Синяя гамма из ТЗ (`#12232E` / `#203647` / `#007CC7` / `#4DA8DA`), которая сейчас лежит в `PRESET_THEMES[0]` под именем Default Dark, **сохраняется как отдельный пресет Deep Blue** — существующие пользователи не теряют привычный вид.

Итоговый список из девяти пресетов:

1. **Neutral Dark** — по умолчанию, занимает слот «Default Dark» из ТЗ
2. **Deep Blue** — сохранённая синяя гамма ТЗ
3. **Default Light** — существующий, без изменений
4. **Midnight Purple**
5. **Ocean Teal**
6. **Minimal Monochrome**
7. **Aurora Emerald**
8. **Glass** — новый, требуется ТЗ §5.4
9. **High Contrast** — новый, обязателен по правилам 16 и 92

ТЗ перечисляет восемь пресетов; девятый — это сохранённый Deep Blue. Расхождение зафиксировано осознанно: удалять существующую тему пользователя ради ровного числа неправильно.

### Обои

Три изменения:

- Строка `url('${value}')` заменяется на переменную `--app-bg-image` с проверкой схемы: разрешены только `https:`, `data:` и `chrome-extension:`.
- Загруженные пользователем картинки идут в IndexedDB через уже существующий `setLarge`, а не в `chrome.storage.local` с его квотой.
- Добавляется **scrim** — затемняющий слой поверх обоев с регулируемой силой, по умолчанию 30 %. Без него текст на светлой фотографии нечитаем; оба референса (HiTab, SuperStart) делают именно так.

### Валидация пользовательского CSS

CSS не исполняет JS, поэтому реальная угроза — **утечка через сетевые запросы**: `@import`, `url()`, `src` в `@font-face`. Владелец такого URL видит факт и время открытия новой вкладки и IP пользователя.

Валидатор:

1. Разбор нативным парсером через конструируемый `CSSStyleSheet` в `try/catch` — заодно отсекается синтаксический мусор.
2. `@import` запрещён всегда.
3. `url()` разрешён только со схемами `data:` и `chrome-extension:`.
4. Устаревшие `behavior` и `-moz-binding` отсекаются.
5. Размер ограничен.

Внешние ресурсы включаются отдельным осознанным тумблером с объяснением последствий: по правилу 32 при конфликте удобства и безопасности выигрывает безопасность, по правилу 112 пользователь должен понимать, на что соглашается. Сброс CSS доступен из настроек всегда, чтобы неудачное правило нельзя было превратить в кирпич.

## 7. Секция 3. Layout Engine и оболочка

### Три типа поверхностей вместо одной карточки

Сейчас `WidgetCard.tsx` оборачивает всё одинаково — стекло, рамка, всегда видимая шапка с заголовком, — из-за чего часы и поиск выглядят как элементы админки, а не как в референсах. В контракт виджета входит поле `surface`:

| Значение | Оформление | Виджеты |
|---|---|---|
| `chromeless` | без фона, без рамки, без шапки — виджет рисует себя прямо по обоям | `clock`, `search` |
| `panel` | стеклянная панель с опциональным заголовком | `weather`, `todo`, `notes`, `rssReader`, `quotes`, `pomodoro`, `systemMonitor`, `iframe` |
| `tiles` | контейнер плиток-иконок с подписями, своя внутренняя сетка и своё перетаскивание | `bookmarks`, `quickLinks` |

`WidgetCard` заменяется на `WidgetShell`, который выбирает обёртку по этому флагу. В `chromeless` элементы управления виджетом (настройки, удаление) живут в оверлее, появляющемся в режиме правки или по наведению, — экран в покое остаётся чистым.

### Каркас

Вариант **A: левый рельс, всегда виден** (как в HiTab). Рельс прижат к левому краю, контент начинается сразу за ним и занимает всю остальную ширину: управление находится без обучения, путь курсора короткий. Отвергнут скрытый док (вариант C): невидимое управление конфликтует с правилом 16 — новый пользователь его не найдёт, а с клавиатуры и через скринридер такой слой требует отдельного механизма раскрытия.

Из рельса открываются: настройки, каталог виджетов, темы, режим правки, импорт/экспорт. Текущие плавающий тулбар (`FloatingToolbar.tsx:29`, `fixed bottom-6 left-1/2 -translate-x-1/2 z-40`) и header с рамкой уходят.

На узком экране (от ~360 px) вертикальный рельс превращается в нижнюю панель с теми же иконками — до неё достаёт большой палец, и требование Mobile First закрывается без отдельной мобильной вёрстки.

### Адаптивная сетка

`RGL` заменяется на `ResponsiveGridLayout` — он уже в зависимостях и не используется. Настройка «12 / 16 / 24 колонки» становится значением для широкого экрана, узкие получают производные:

| Брейкпоинт | Ширина | База 12 | База 16 | База 24 |
|---|---|---|---|---|
| `xl` | ≥ 1200 px | 12 | 16 | 24 |
| `lg` | 900–1199 px | 8 | 12 | 16 |
| `md` | 640–899 px | 6 | 8 | 8 |
| `sm` | 360–639 px | 4 | 4 | 4 |
| `xs` | < 360 px | 2 | 2 | 2 |

Ниже двух колонок сетка не опускается никогда. Значение `sm = 4` соответствует согласованному макету: iPhone SE — 375 px — четыре колонки.

Раскладка хранится **отдельно для каждого брейкпоинта и заполняется лениво**: пока пользователь не правил композицию на телефоне, она выводится из ближайшей заполненной; после первой правки становится независимой. Перестановка виджетов на ноутбуке больше не ломает вид на телефоне.

`rowHeight={90}` уходит: высота ряда считается из ширины ячейки так, чтобы ячейка оставалась квадратной, с ограничением примерно 72–140 px. Без верхней границы виджет 4×2 на 4K превратился бы в баннер 1200×600.

`max-w-7xl` из `App.tsx:64` убирается: избыточная ширина на больших экранах уходит в увеличенные поля по краям, а не в жёсткую обрезку контента.

### Правка раскладки как отдельный режим

Перетаскивание и изменение размера включены только в режиме правки. В обычном режиме виджеты не сдвигаются от случайного промаха, а выделение текста в заметках не превращается в перетаскивание.

### Взаимодействие и доступность

- Внутри `tiles` порядок меняется через `@dnd-kit/sortable` (~10 КБ). Зависимость оправдана ровно одним: она даёт перетаскивание **с клавиатуры**, которого нет в `react-grid-layout` (правило 41 — обоснование обязательно). Это единственная новая зависимость в UI-слое, и она добавляется ради доступности, а не удобства реализации.
- В режиме правки работает клавиатура: стрелки перемещают выбранный виджет по сетке, `Shift` + стрелки меняют размер, `Escape` выходит из режима.
- Зоны нажатия доводятся до 44×44 (сейчас ручка ресайза 14 px, кнопки шапки ~24 px). Визуально ручка остаётся мелкой — растёт только зона попадания.

### Состояния

Loading, empty, error, no-permission, offline закрываются тремя переиспользуемыми компонентами (`Skeleton`, `EmptyState`, `ErrorState`) плюс `ErrorBoundary` внутри `WidgetShell`. Сейчас в проекте нет ни одного `ErrorBoundary`, и один упавший виджет уносит весь дашборд.

## 8. Секция 4. Контракты, хранилище, i18n

Это слой, на котором заклинило всё остальное: i18n невозможен, потому что имена виджетов — строки; code splitting отсутствует, потому что компоненты импортируются статически; типизации настроек нет, потому что везде `any`.

### Контракт виджета

`types.ts` меняется в четырёх местах:

1. `name` и `description` становятся **ключами локализации**. Русские имена перестают лежать внутри реестра.
2. `component` заменяется на **`load: () => Promise<{ default: ComponentType<WidgetProps<S>> }>`**, чтобы `React.lazy` подтягивал компонент по требованию. Это и есть отсутствующий code splitting: сейчас первый экран тянет все 12 виджетов, даже если на дашборде три, при заявленной в ТЗ цели загрузки быстрее двух секунд.
3. **Дженерик настроек вместо `any`**: `WidgetDefinition<S>` фиксирует тип настроек, компонент получает `settings: S`, а схема полей описывает их через `keyof S` — опечатка в имени поля перестаёт компилироваться. Типы полей дополняются отсутствующими `slider`, `color`, `multiselect`.
4. `permissions?: string[]` заменяется на **union** `'storage' | 'network' | 'bookmarks' | 'geolocation'` — ровно то, что реально нужно двенадцати виджетам и шаблонам декларативных плагинов. Строки непроверяемы, а от этого списка зависит доступ плагина к данным.

### Схема настроек как валидатор

Схема используется дважды: она рисует форму **и проверяет данные, прочитанные из хранилища**. Сохранённые данные после миграции или правки JSON руками — это недоверенный ввод, и правило 25 требует относиться к нему именно так. Валидатор пишется на той же схеме, примерно 50 строк, без `zod` (правило 41).

### Идентификаторы и неизвестные виджеты

Внутри кода идентификаторы виджетов становятся union из реестра манифестов и остаются строками только на границе хранилища, где может прийти что угодно: старый id, удалённый плагин, чужой импорт. Сейчас этот случай обработан плохо — `GridEngine.tsx:65` ставит в заголовок `item.widgetId.toUpperCase()`, а тело отдаёт `PluginHost`, который для встроенного виджета не рисует ничего. Вместо этого неизвестный виджет получает явное состояние «виджет недоступен» с кнопкой удаления.

### Хранилище, версии, миграции

У `persist` в `useDashboardStore.ts` нет ни `version`, ни `migrate` (задан только `name: 'dashflow_dashboard_store'`), при этом форма данных меняется: раскладки по брейкпоинтам, типизированные настройки, флаги скрытия и блокировки. Без миграции существующая установка получит сломанный дашборд.

- Каждый persist-стор получает `version` и `migrate`.
- Миграция v1 → v2 переносит `{x, y, w, h}` в раскладку широкого брейкпоинта и прогоняет настройки через валидатор схемы.
- Миграция — чистая функция в `core/storage`, покрытая unit-тестами.
- Перед миграцией предыдущее состояние копируется в отдельный ключ для откота (правило 51); цена — несколько килобайт.

Поведение при ошибках меняется: `StorageAdapter` сейчас глотает всё в `console.warn` и возвращает значение по умолчанию. Для чтения это приемлемо, для записи — нет: при переполнении квоты пользователь должен увидеть, что настройки не сохранились.

Ключи переезжают в типизированный реестр. Обои уходят в IndexedDB через существующий `setLarge`. В `chrome.storage.sync` остаётся только мелочь — язык и выбранная тема; документация, обещающая `sync` для всего, исправляется, потому что раскладка туда физически не влезает.

### i18n

- Ключи выводятся из структуры русской локали рекурсивным типом; рукописный union на 30 записей в `i18n.ts` уходит.
- Появляются интерполяция и плюрализация через `Intl.PluralRules`.
- Даты и числа переходят на `Intl.DateTimeFormat` и `Intl.NumberFormat` — сейчас часы и RSS форматируют вручную.
- Локали загружаются динамическим импортом, чтобы английский не попадал в бандл русскоязычного пользователя.
- Тест сравнивает наборы ключей между языками (правило 94). Отсутствующий ключ отдаёт fallback-язык, а не сам ключ (правило 43.12).
- В `translations.widgets` дописываются пять недостающих имён виджетов.
- В манифест добавляются `default_locale` и `_locales`: описание расширения сейчас захардкожено по-русски в `wxt.config.ts`.

## 9. Секция 5. Плагины, каталог, безопасность

Отправная точка — факт, определяющий всю секцию: `PluginHost.tsx` рисует внутри `srcDoc` карточку с надписью «Запущен в изолированной песочнице (Sandbox Frame)» и ничего не загружает; проп `scriptUrl` объявлен и не используется. Вызывается он только тогда, когда `WidgetRegistry.get()` вернул `undefined`, а все 12 виджетов каталога зарегистрированы как встроенные — включая `rssReader`, помеченный в каталоге как `type: 'sdk'`. То есть SDK-слоя не существует, а путь «плагин» фактически совпадает с путём «виджет не найден». Этот путь превращается в состояние «виджет недоступен» из секции 4, а песочница переписывается.

### Декларативные плагины

Плагин — это JSON-манифест без кода: источник RSS, встроенная страница, набор ссылок, шаблон API-виджета. Рисуют его встроенные шаблонные компоненты. Внешнего кода нет вообще, поэтому запрет MV3 на удалённо размещённый код выполняется буквально: JSON — это данные, а не скрипт (ADR-001).

Манифест валидируется той же машинерией схем, что и настройки виджета. Источник — файл или ручной ввод; загрузки с сервера в MVP нет.

### Мост в песочницу

Сейчас `handleMessage` проверяет только `e.data.source !== 'dashflow-plugin'` и отвечает в `'*'`; слушатель навешивается на `window` для каждого экземпляра, и каждый из них обрабатывает каждое сообщение. Значит любой фрейм страницы может записать в `plugin_<любой id>_<ключ>`, а «свой» id плагина берётся из замыкания хоста, а не из проверенного источника.

Правильная проверка — по окну, а не по origin: `sandbox="allow-scripts"` без `allow-same-origin` даёт фрейму origin `null`, поэтому отправитель определяется как `event.source === iframe.contentWindow`, а ответ адресуется в `'null'`. Слушатель — один на приложение, маршрутизация по совпадению окна.

### Встраивание сайтов

`IframeWidget.tsx:36` содержит `sandbox="allow-scripts allow-same-origin allow-forms"`, а URL берётся как `settings?.url || 'https://wxt.dev'` без проверок; настройки приходят и через импорт JSON, то есть это недоступный доверию ввод, куда можно подставить произвольную схему, включая адрес внутри самого расширения. Схема ограничивается `https:`, `allow-same-origin` убирается. Неиспользуемый импорт `RefreshCw` удаляется.

### Конвейер RSS

Три отдельные проблемы:

1. `link` из XML попадает прямо в `href` без проверки схемы — закрывается проверкой на `https:`/`http:`.
2. `thumbnail` попадает в `<img src>` — это пиксель, раскрывающий владельцу ленты IP и время открытия новой вкладки; картинки становятся отдельным согласием.
3. Безусловный fallback на публичный прокси (`RssWidget.tsx:61`) отдаёт третьей стороне список того, что читает пользователь; он перестаёт быть автоматическим и становится явной опцией с предупреждением.

Фоновый запрос получает таймаут и лимит размера — сейчас нет ни того, ни другого, и `chrome.runtime.lastError` не проверяется. Закрываются также пустой экран при отказе всех лент и расхождение с CHANGELOG: обещанного «единого хронологического потока» в коде нет (элементы идут сгруппированными по лентам), а комментарий про сортировку стоит над строкой, которая ничего не сортирует.

### Права и манифест

Права сегодня — это подпись в карточке; нажатие «Добавить на экран» устанавливает виджет молча. Появляется экран согласия перед установкой; согласие хранится вместе с версией манифеста; расширение прав требует нового согласия; отзыв доступен в настройках; проверка происходит **в точке доступа к данным**, а не только в UI.

`host_permissions: ['<all_urls>']` сужается до конкретных адресов, которые действительно используются:

- `https://api.open-meteo.com/*` — погода (`WeatherWidget.tsx:22`)
- `https://images.unsplash.com/*` — обои (`ThemesModal.tsx:21`)

Пользовательские ленты и встраиваемые сайты переезжают в `optional_host_permissions` и запрашиваются в момент добавления. Публичный прокси не попадает в манифест по умолчанию: он запрашивается только при включении соответствующей опции.

Добавляется явный `content_security_policy`:

- `extension_pages`: `script-src 'self'; object-src 'self'; frame-src https:`
- `sandbox`: `sandbox allow-scripts; script-src 'self'; object-src 'none'`

### Каталог

Каталог переезжает из `MarketplaceModal.tsx:33` в данные: сейчас он дублирует реестр вторым списком, и списки уже разошлись — `rssReader` 1.1.0 в каталоге против 1.0.0 в реестре, размеры продублированы рядом с `defaultSize`. Реестр становится источником правды, JSX-иконки заменяются на `iconName`, имена и категории уходят в локали, добавляются поиск и состояния загрузки/пустоты/ошибки. Кнопка «Удалить» перестаёт снимать случайный первый экземпляр из нескольких.

## 10. Секция 6. Качество, проверки, документация

### Границы ошибок

`ErrorBoundary` идёт в `WidgetShell`: на месте упавшего виджета появляется карточка «виджет не загрузился» с кнопкой перезагрузки, остальные продолжают работать. Второй boundary — в корне приложения, на случай падения самой оболочки. Ошибка логируется **без содержимого настроек**: там могут быть личные адреса и города.

### Доступность

Часть требований правила 16 закрыта решениями выше: 44×44 и фокус — в секции 3, `aria-label` вместо русского `title` — там же, контраст и скрим — в секции 2. Здесь остаётся:

- focus trap и возврат фокуса в модалках и drawer'ах;
- `Escape` на закрытие;
- `aria-live` для асинхронных обновлений (погода, RSS);
- уважение `prefers-reduced-motion` для всех анимаций;
- проход по всей вкладке только с клавиатуры;
- одна проверка скринридером.

### Тесты

`environment: 'node'` в `vitest.config.ts:11` физически мешает тестировать компоненты, поэтому добавляются `jsdom` и `@testing-library/react`. Пирамида сознательно узкая: это расширение, а не банковский бэкенд.

Обязательные unit-тесты там, где ошибка молча портит данные пользователя:

- миграции хранилища;
- валидатор настроек и манифеста;
- валидатор пользовательского CSS;
- проверки схем URL;
- расчёт числа колонок и высоты ряда из ширины;
- вывод ключей локализации и сравнение наборов ключей между языками.

Компонентные тесты — на состояния из правила 18: loading, empty, error, no permission.

Негативные проверки безопасности из секции 5: сообщение из чужого окна отвергается; ссылка `javascript:` не доходит до `href`; плагин без согласия не читает хранилище.

E2E в этот заход не входят: они требуют запуска расширения в реальном Chrome через отдельный раннер, а до появления линтера, тестов и CI дают меньше пользы на единицу работы. Решение пересматривается после первого релиза.

### Линтер и CI

ESLint с правилами React Hooks и TypeScript плюс Prettier ловят то, что сейчас ловится глазами: неиспользуемые импорты (`RefreshCw` в `IframeWidget`), `any`, зависимости эффектов. Порядок CI по правилу 65 — lint, `tsc --noEmit`, тесты, `wxt build`; на красном не мержим. `@types/react-grid-layout` переезжает из `dependencies` в `devDependencies`.

### Документация

Восемь файлов в `docs/` расходятся с кодом, и правило 6 требует устранить это в том же изменении:

- `PLUGIN_SDK_ARCHITECTURE.md` — переписывается под декларативную модель;
- `THEME_ENGINE_ARCHITECTURE.md` — под новый контракт токенов и переименованный пресет;
- `LAYOUT_ENGINE_ARCHITECTURE.md` — под адаптивный движок;
- `SECURITY_ARCHITECTURE.md` — под модель угроз и права из секции 5;
- `WIDGET_ENGINE_ARCHITECTURE.md` — под новый контракт виджета и ленивый реестр;
- `CORE_ARCHITECTURE.md` — под новую структуру слоёв;
- `technical specifications.md` — исправляется ссылка на `src/pages/`: WXT требует точку входа в `src/entrypoints/`, поэтому ошибка в документе, а не в коде;
- `CHANGELOG.md` — сохраняется установленный формат `[NEW]` / `[MODIFY]`, по записи на этап, с миграциями и откатом.

## 11. Порядок работ

Стратегия «фундамент → слои»: шесть этапов снизу вверх. После каждого проект собирается и работает; ни один не оставляет дашборд сломанным.

| Этап | Содержание | Ключевой результат |
|---|---|---|
| 1 | Токены, шкалы, дизайн-система, `ui/primitives` и `ui/overlays` | визуальный язык существует, старые экраны на нём перерисованы |
| 2 | Контракты виджета, типизированные настройки, реестр ключей хранилища, `version` + `migrate`, i18n-движок | данные типизированы, миграция протестирована |
| 3 | Оболочка: левый рельс, `WidgetShell`, три поверхности, `ResponsiveGridLayout`, скрим, режим правки | новый вид и адаптивность от 360 px до 4K |
| 4 | Виджеты по одному: разбиение крупных, ленивая загрузка, состояния, уход `<table>` | 12 виджетов на новом контракте |
| 5 | Декларативные плагины, песочница, согласие на права, единый каталог, RSS-конвейер, CSP и host permissions | плагины и каталог реально работают |
| 6 | Тесты, ESLint, Prettier, CI, документация, ADR, CHANGELOG | зелёный CI и документация, соответствующая коду |

### Definition of Done этапа

Этап закрыт, когда одновременно верно:

1. `tsc --noEmit` без ошибок.
2. `vitest run` зелёный, и тесты этапа действительно существуют (пустой набор не считается).
3. `wxt build` собирается.
4. Проверена ширина 360 px и одна крупная (≥ 2560 px) — без горизонтального скролла, обрезки и наложений.
5. Пройден путь только с клавиатуры по затронутым экранам.
6. Состояния loading / empty / error / no-permission присутствуют там, где применимы.
7. Обновлены соответствующие `docs/*_ARCHITECTURE.md` и `docs/CHANGELOG.md`.
8. Выполнен self-review по правилу 26.

Существующая установка расширения после каждого этапа открывается и показывает дашборд — это проверяется вручную на профиле с данными от предыдущей версии.

## 12. Миграции, откат, жизненный цикл данных

### Затрагиваемые хранилища

| Ключ | Что меняется | Миграция |
|---|---|---|
| `dashflow_dashboard_store` | `{x, y, w, h}` → раскладки по брейкпоинтам; настройки прогоняются валидатором; добавляются флаги скрытия и блокировки | v1 → v2, чистая функция, unit-тесты |
| `theme_active_id` | `default-dark` переименовывается в `deep-blue`; новым значением по умолчанию становится `neutral-dark` | точечное переименование в той же миграции |
| `theme_colors`, `theme_bg`, `theme_custom_css` | переезжают под общий persist-стор темы с `version` | v1 → v2 |
| обои, загруженные пользователем | из `chrome.storage.local` в IndexedDB через `setLarge` | перенос при первом чтении, старый ключ очищается после успешной записи |

### Откат

- Перед миграцией предыдущее состояние копируется в `dashflow_backup_v1` (и аналог для темы). Пользователь может вернуться на предыдущую версию расширения, и она прочитает свои данные.
- Резервная копия удаляется по явному действию пользователя в настройках, а не автоматически.
- Пользовательский CSS всегда сбрасывается кнопкой в настройках — неудачное правило не превращает страницу в кирпич.
- Импорт/экспорт JSON остаётся ручным способом восстановления и получает валидацию по схеме на входе.

### Жизненный цикл данных

Все данные локальны и не покидают устройство. Удаление расширения удаляет `chrome.storage` и IndexedDB. В настройках доступны экспорт (JSON) и полный сброс. Срок хранения — бессрочный до действия пользователя; автоматической отправки телеметрии и аналитики нет и не добавляется.

## 13. Риски

| Риск | Вероятность | Последствие | Меры |
|---|---|---|---|
| Миграция ломает дашборд существующего пользователя | средняя | потеря раскладки | чистая функция + unit-тесты + резервная копия перед записью + ручная проверка на профиле с данными v1 |
| Смена палитры по умолчанию воспринимается как потеря темы | средняя | недовольство | синяя гамма сохранена как **Deep Blue**, активная тема пользователя переименовывается, а не заменяется |
| `ResponsiveGridLayout` ведёт себя иначе, чем текущий `RGL` | средняя | скачки раскладки | раскладки по брейкпоинтам заполняются лениво; проверка на пяти ширинах в DoD этапа 3 |
| Квадратная ячейка с ограничением 72–140 px даёт неудачные пропорции у части виджетов | средняя | визуальные дефекты | проверка всех 12 виджетов на трёх ширинах на этапе 4; при необходимости корректируются `defaultSize`, а не механизм |
| Строгая валидация CSS ломает существующий пользовательский CSS | низкая | стиль перестаёт применяться | понятное сообщение о том, какое правило отклонено, вместо молчаливого игнорирования; сброс всегда доступен |
| Сужение `host_permissions` ломает пользовательские ленты | средняя | RSS перестаёт грузиться | `optional_host_permissions` запрашиваются в момент добавления ленты; при отказе — состояние no-permission с кнопкой запроса |
| Объём работ шести этапов превышает ожидания | высокая | затягивание | каждый этап самодостаточен и оставляет проект рабочим; остановка возможна после любого |
| `@dnd-kit/sortable` увеличивает бандл | низкая | +~10 КБ | оправдано клавиатурным перетаскиванием (правило 16); подключается только в `tiles`-поверхности |
| Ленивая загрузка даёт кадр со скелетоном там, где содержимое появлялось сразу | высокая | дёргается сетка | скелетон занимает ровно место виджета: размер берётся из раскладки, а не из содержимого |
| Отказ от `allow-same-origin` ломает часть встраиваемых страниц | средняя | страница не отображается | осознанная плата за изоляцию; в интерфейсе появляется явное сообщение, если страница отказалась встраиваться, с подсказкой открыть её в новой вкладке |

### Открытые вопросы

Требуют решения в ходе работ, не блокируют утверждение спеки:

1. **`prefers-color-scheme`.** Переключать светлую и тёмную темы автоматически по системной настройке или оставить выбор полностью за пользователем — решается на этапе 1. Безопасный вариант по умолчанию: выбор пользователя приоритетнее системы, автоматический режим доступен как отдельный пункт «Как в системе».
2. **Сортировка лент RSS.** Смешивать элементы разных лент по дате в единый поток или группировать по источнику — решается на этапе 4 при разборе `RssWidget`. CHANGELOG обещает единый хронологический поток, код его не делает; расхождение устраняется в любом случае — вопрос только в том, какое поведение станет верным.

## 14. Acceptance criteria

Формулировки проверяемые: каждая либо выполняется, либо нет.

**Дизайн и адаптивность**

1. На ширинах 360, 375, 768, 1440, 2560 и 3840 px нет горизонтального скролла, обрезанного контента и наложений.
2. Часы и поиск отрисованы без карточки, рамки и шапки; закладки и быстрые ссылки — плитками с подписями; остальные — стеклянными панелями.
3. На ширине < 640 px в дашборде нет ни одного элемента `<table>`.
4. На 4K избыточная ширина уходит в поля: ячейка сетки не превышает 140 px по высоте.
5. Все девять пресетов применяются целиком: в DOM нет цветов вне палитры активной темы.
6. Пресет High Contrast обеспечивает контраст текста к фону не ниже 4.5:1.
7. Все анимации в диапазоне 150–250 ms и отключаются при `prefers-reduced-motion: reduce`.

**Контракты и данные**

8. `any` отсутствует в `src/core/widget/types.ts` и в определениях всех 12 виджетов.
9. Первый экран не загружает код виджетов, отсутствующих на дашборде (проверяется составом чанков сборки).
10. Профиль с данными предыдущей версии открывается после миграции с сохранённой раскладкой; резервная копия создана.
11. Настройки, прочитанные из хранилища и не прошедшие схему, заменяются значениями по умолчанию, а не ломают виджет.
12. Неизвестный `widgetId` даёт состояние «виджет недоступен» с работающей кнопкой удаления.

**i18n**

13. В `src/` нет пользовательских строк вне локалей.
14. Наборы ключей русской и английской локали совпадают (проверяется тестом).
15. Отсутствующий ключ отдаёт fallback-язык; ключ локализации пользователю не показывается никогда.
16. Даты, числа и множественные формы форматируются через `Intl`.

**Безопасность**

17. `@import` и `url()` с внешней схемой в пользовательском CSS отклоняются с понятным сообщением.
18. Обои принимают только `https:`, `data:`, `chrome-extension:`.
19. `IframeWidget` не содержит `allow-same-origin` и принимает только `https:`.
20. Ссылка `javascript:` из RSS не попадает в `href` (проверяется тестом).
21. Сообщение из окна, не являющегося `iframe.contentWindow`, отвергается (проверяется тестом).
22. Установка плагина невозможна без экрана согласия; согласие хранится с версией манифеста.
23. `host_permissions` не содержит `<all_urls>`; заданы `content_security_policy` для `extension_pages` и `sandbox`.
24. Публичный прокси и загрузка картинок из лент выключены по умолчанию.

**Качество**

25. Падение любого виджета не уносит дашборд: остальные продолжают работать.
26. Модалки и drawer'ы удерживают фокус, возвращают его и закрываются по `Escape`.
27. Интерактивные элементы имеют зону нажатия не менее 44×44 px.
28. Вся вкладка проходится с клавиатуры, включая перемещение виджетов.
29. `npm run lint`, `tsc --noEmit`, `vitest run`, `wxt build` зелёные; тесты из перечня секции 10 существуют.
30. Все восемь документов в `docs/` соответствуют коду; ADR из раздела 15 созданы; `CHANGELOG.md` содержит запись на каждый этап.

## 16. Зафиксированные допущения

Явно, чтобы их можно было оспорить при вычитке:

1. **Целевой браузер — Chrome.** Кросс-браузерная поддержка не проверяется в этот заход.
2. **Пользователь один, устройство личное.** Ролей, организаций и разделения доступа нет.
3. **Серверной части не появится в рамках этой работы.** Каталог локальный, загрузки с сервера нет.
4. **Русский — основной язык, английский — второй.** RTL-язык не добавляется, но логические CSS-свойства используются сразу, чтобы добавление не требовало переписывания (правило 43.6).
5. **Существующие пользователи есть, и их данные надо сохранить.** Отсюда обязательные миграции и резервная копия. Если установок в реальности нет, миграции всё равно остаются: они дешевле, чем разбор жалоб.
6. **`docs/technical specifications.md` — источник требований, но не истина о структуре кода.** Расхождение по `src/pages/` решается в пользу кода.
