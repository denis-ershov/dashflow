# ADR-023. Локальный Hub и версия записи при синхронизации

**Принято** 2026-11-24.

## Контекст

Расширение должно сохранять работоспособность офлайн. Автоматизации и другие профили браузера получают доступ к общим записям через Hub, которым управляет владелец. Потеря ответа, остановка фонового процесса или конкурирующие правки не должны приводить к тихой потере текста.

## Решение

Hub слушает loopback по умолчанию и хранит данные в SQLite через встроенный `node:sqlite`. Fastify обрабатывает запросы, а изменения содержимого, журнал и ключ идемпотентности сохраняются транзакционно. Общие типы и валидаторы выделены в `packages/shared`.

Расширение сохраняет снимки исходящих правок в IndexedDB вместе с данными. При синхронизации большее число версии побеждает. При равенстве побеждает версия Hub. Отличающийся проигравший снимок остаётся в истории. WebSocket сигнализирует, что нужно дочитать последовательный REST-журнал, поэтому пропуск уведомления не влияет на полноту данных.

## Альтернативы

- `better-sqlite3` даёт зрелый SQLite API с нативной зависимостью. Встроенный модуль позволяет использовать одинаковый способ установки в Windows, macOS, Linux и контейнерах.
- Синхронизация по времени изменения проще для досок, но зависит от часов клиентов. Номер версии сохраняет причинную последовательность, а Hub разрешает ничью одинаково для всех устройств.
- Слияние каждого поля и CRDT могут сохранить больше параллельных изменений, но потребуют отдельного формата и правил для порядка, архива и удаления. Снимки истории оставляют возможность прочитать проигравшую правку.

## Последствия

Для локального Hub требуется Node 22.13+. SQLite остаётся базой одного экземпляра Hub. Рост журнала и история требуют места для хранения и резервирования. Для отката браузера с IndexedDB v2 используется актуальный JSON-экспорт и отдельный профиль. Полные процедуры описаны в [руководстве Hub](../HUB_OPERATIONS.md) и [стратегии резервного копирования](../BACKUP_STRATEGY.md).
