# Архитектура API DashFlow Hub

## Назначение и границы

Hub — локальный HTTP-сервис для доступа к данным DashFlow агентами и синхронизации браузерного расширения. API v1 описан в [`hub/openapi.yaml`](../hub/openapi.yaml); реализация находится в `hub/src/http/`, предметные операции и хранение — в `hub/src/db/`. Конфигурация запуска и команды CLI описаны в [`HUB_OPERATIONS.md`](HUB_OPERATIONS.md).

Hub не является публичным multi-tenant SaaS. По умолчанию он слушает `127.0.0.1:47831`; для удалённого доступа требуется отдельная TLS-терминация и защищённая сеть. HTTP reverse proxy не является частью Hub и его заголовки не участвуют в аутентификации.

## Компоненты и ответственность

- `hub/src/http/index.ts` создаёт Fastify-сервер, задаёт общие лимиты, CORS/Origin, формат ошибок, аудит HTTP-записей и регистрирует REST, WebSocket и webhook маршруты.
- `hub/src/http/access.ts` проверяет Bearer-токены, scopes, Origin и локальные оконные rate limits. Контекст principal хранится на время запроса.
- `hub/src/http/validation.ts` проверяет тела, query-параметры, идентификаторы, версии и ключи идемпотентности. Неизвестные поля объектов отклоняются.
- `hub/src/http/rest.ts` связывает HTTP-контракты с операциями репозитория: items, boards, digests, history и синхронизация.
- `hub/src/http/stream.ts` обслуживает WebSocket. Он требует Origin расширения и `sync`-токен в первом сообщении после upgrade; сервер сообщает sequence изменений, а содержимое клиент получает через `/v1/changes`.
- `hub/src/http/webhooks.ts` проверяет подпись по исходным байтам JSON, временное окно и id доставки, затем создаёт item во входящих.
- `hub/src/db/index.ts` реализует предметные операции, проверку версий/владельцев, курсорную выборку и журнал изменений.
- `hub/src/db/credentials.ts` управляет токенами, pairing challenge, webhook credentials и audit-записями.
- `hub/src/db/schema.ts` создаёт схему SQLite и выполняет транзакцию миграции.
- `packages/shared/src/` — общий источник типов и проверок Item/Board и sync snapshot для Hub и расширения.

## Потоки данных

### REST-запись

Клиент отправляет JSON и Bearer-токен. Fastify применяет общий лимит тела (256 KiB), таймаут (15 секунд) и проверку Origin. Для маршрута проверяются токен и требуемый scope, затем входные данные валидируются. Репозиторий выполняет SQLite-операцию в транзакции, обновляет payload и журнал `changes`; запись предметной операции также добавляет audit-событие. После успешной записи HTTP-маршрут уведомляет подключённые stream-клиенты о новом sequence.

Ошибки возвращаются как `{ error: { code, message, details? } }`. Внутренние исключения не раскрываются клиенту; ошибка audit-записи не превращает уже выполненную операцию в неуспешный ответ.

### Чтение и ownership

`GET /v1/items` возвращает общую для Hub выборку с фильтрами и курсором; стандартно исключены архивные и удалённые элементы. `GET /v1/items/{id}` также доступен любому токену со scope `items:read`. Это не персональное хранилище с изоляцией чтения по владельцу.

Новые items получают `owner_id`, равный principal id токена или webhook-коннектора. `PATCH /v1/items/{id}` требует `items:write`, совпадающий `If-Match` и принадлежность владельцу; чужой item можно менять только токеном с `items:manage`. `DELETE` — мягкое удаление и требует `items:manage`; `If-Match` для удаления необязателен. Доски читаются и изменяются по scope, но текущая реализация не проверяет ownership доски и не требует версию при PATCH. Эти свойства должны учитываться при выдаче scopes.

`/v1/changes` отдаёт общий журнал Hub всем клиентам со scope `sync`, без фильтра по владельцу. `GET /v1/items/{id}/history` также требует `sync` и адресует историю по id. Поэтому `sync` является широким доступом ко всем синхронизируемым данным Hub, а не ограниченным scope устройства.

### Pairing и синхронизация расширения

CLI создаёт одноразовый challenge: случайный шестизначный код хранится как scrypt-хеш с солью, срок действия — пять минут, максимум неверных попыток — десять. Challenge может быть связан с Origin. `POST /v1/pair` проверяет настроенный точный Origin и обменивает код на токен только со scope `sync`; токен возвращается клиенту один раз.

После pairing расширение хранит токен в локальном хранилище браузера. Очередь исходящих изменений хранится на стороне расширения, отправляется через `/v1/sync/push`, повторяется с идемпотентным ключом. Hub принимает пакет из 1–50 изменений; каждая запись проходит общую проверку snapshot. Версия выше текущей применяется с сохранением owner существующей записи; при создании owner становится id отправившего principal. Устаревшая версия не применяется (`applied: false`); отличающаяся версия записывается в `item_history` для разрешения конфликта клиентом.

При наличии активной вкладки клиент использует `/v1/stream`: после WS upgrade он отправляет `{ "type": "authenticate", "token": "…" }`, получает `ready`, а затем поддерживает соединение сообщениями `ping` и принимает `pong`. Сообщение `changes` содержит только sequence; содержимое изменений читается обычным REST-запросом. При отсутствии stream расширение может опрашивать `/v1/changes` с `since`.

### Webhook

Входящий маршрут не использует Bearer и запрещает заголовок Origin. Подпись HMAC-SHA256 строится по UTF-8 строке `timestamp.delivery.` и точным исходным байтам тела; метка времени в миллисекундах должна быть не старше пяти минут. HMAC сравнивается в постоянное время до JSON-разбора. Идентификатор доставки служит ключом идемпотентности. Webhook создаёт item со статусом `inbox`; его токен пути и signing key — секреты.

## Контракт, зависимости и эксплуатационные ограничения

- Scope токена проверяется на сервере для каждого защищённого маршрута: `items:read`, `items:write`, `items:manage`, `boards:read`, `boards:write`, `digests:write`, `sync`.
- Записывающие запросы ограничиваются по токену; стандарт — 60 запросов в минуту, конфигурационный диапазон — 1–10 000. Pair ограничен 10 запросами/мин на IP и 30/мин глобально. Неуспешная аутентификация и WS handshake ограничены на IP; webhook — отдельно на IP и webhook principal. Ограничители и счётчики in-memory, не распределены между несколькими процессами.
- CORS разрешает только точные `chrome-extension://<id>` и `moz-extension://<uuid>` из конфигурации. HTTP-клиенты без браузера всё равно должны предоставить токен; CORS не является механизмом авторизации.
- SQLite использует `node:sqlite`, WAL, `busy_timeout=5000`, транзакции `BEGIN IMMEDIATE` и параметризованные запросы. База Hub имеет независимую от базы расширения схему.
- API зависит от Fastify, `@fastify/websocket`, встроенного Node SQLite и пакета `@dashflow/shared`. Версии и конфигурация приведены в `hub/package.json` и lock-файле.
- WebSocket ограничен 256 соединениями, 1024 байтами на кадр и закрывает клиента при превышении буфера 64 KiB. Аутентификация после upgrade должна завершиться за пять секунд; ping принимается не чаще одного раза в пять секунд.

## Схема данных, миграции и откат

SQLite schema version 1 содержит `items`, `boards`, `changes`, `item_history`, `idempotency`, `tokens`, `audit`, `webhooks` и `pairing_challenges`. Payload сущностей хранится JSON-текстом и валидируется общими схемами. Таблица `changes` — последовательный журнал; `item_history` хранит проигравшие/сохранённые версии для конфликтов; idempotency ключ уникален в рамках principal и операции.

Миграции выполняются при открытии базы. Текущий код принимает пустую базу (версия 0) и создаёт версию 1; неизвестная версия останавливает запуск. Обратной миграции или автоматического downgrade нет. Перед будущим изменением схемы следует добавить атомарную миграцию, определить совместимость версии приложения и базы, а до развёртывания сделать проверенную SQLite-копию вместе с WAL sidecar при необходимости.

Откат приложения не должен сопровождаться понижением schema version или ручным удалением таблиц. Если новая версия уже мигрировала данные, восстановление выполняется из согласованной резервной копии по процедуре `docs/HUB_OPERATIONS.md`; это может потерять записи после момента backup. Для текущего OpenAPI/документационного изменения миграции не требуются.

## Проверки и границы подтверждения

По результатам команды проекта серверные тесты и три повтора E2E с двумя синтетическими Chromium-профилями прошли. E2E использовал временно разрешённый loopback-хост и проверял фактический Origin, WebSocket, повтор очереди после ответа 503 и конфликт версий. Это подтверждение указанных сценариев в тестовой среде; оно не подтверждает работу Firefox, NVDA, Docker или публичного развёртывания.
